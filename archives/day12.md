## Day12｜评测版本化：让每一个分数都可解释、可复现

今天的目标：把上一阶段的 `gold_labels.jsonl → predictions_run.jsonl → metrics.json / failures.jsonl / release_decision.json` 闭环，升级为一份可审计的评测运行记录。完成后，看到“准确率从 91% 降到 86%”时，你能回答：究竟是模型、prompt、数据、评测器，还是运行环境变了。

### 先回顾：为什么不能只保存 accuracy？

`accuracy=0.91` 本身不是一个可比较的实验结果。它至少遗漏了四类会改变分数含义的变量：

```text
dataset_version：测试样本、金标、切分或数据快照是否改变
prompt_version ：system prompt、few-shot 示例、解码参数是否改变
model_version  ：模型/adapter/checkpoint/服务端模型版本是否改变
evaluator_version：schema 规则、evidence 校验和指标实现是否改变
```

例如，把 `unknown` 的 evidence 规则从“必须为空”放宽为“可为空或可填写相关文本”，JSON/schema 合法率可能上升；这并不证明模型更可靠，而可能只是评测器变宽松。反过来，换了一批更难、更贴近线上长尾的测试样本，accuracy 下降也不等于模型退化。

因此，一次评测的最小因果链应当是：

```text
固定输入与规则
(dataset + prompt + model + evaluator + runtime)
        ↓
生成原始答卷 predictions_run.jsonl
        ↓
评测器产出 metrics.json / failures.jsonl
        ↓
门槛规则产出 release_decision.json
```

`run_manifest.json` 是这条链的“实验身份证”：它不取代原始答卷或指标文件，而是把它们使用的版本、输入、产物与执行上下文绑定到同一个不可混淆的 `run_id`。

## 哈希是什么？

可以把 SHA-256 哈希理解为文件内容的“指纹”。它将任意文件计算成一串固定长度的字符，例如：

~~~text
predictions_run.jsonl 的内容
        ↓ SHA-256
7f83b1657ff1fc53b92dc18148a1d65d…
~~~

它不是秘密，也不用于加密。它回答的是：我今天看到的这个文件，是否仍是当时评测用的那一个字节不差的文件？

- 内容一字不改 → 哈希相同；
- 改一个预测标签、删一行、换一个空格或换行 → 哈希都会变；
- 对不同内容发生相同 SHA-256 的概率在工程上可忽略，因此可把哈希当作内容身份。

为什么 IV 缺少它会影响审计？设评测目录始终叫 runs/latest/predictions_run.jsonl：

~~~text
9:00  ckpt-4200 的预测写入该路径，算出 accuracy=91%
10:00 ckpt-4600 的预测覆盖同一路径，算出 accuracy=88%
16:00 有人重跑或手工修正该文件，但路径名没变
下周  只能看到路径与两个指标，无法证明两个 metrics 分别来自哪一版预测
~~~

没有预测文件的哈希（或等价的不可变对象版本/只读存储 ID），后来的人无法验证：

1. metrics.json 是否确由所声明的 predictions_run.jsonl 计算得到；
2. 该预测文件是否在指标生成后被覆盖或修改；
3. A、B 是否各自使用了正确、完整的答卷。

所以 IV 的正确处置不是重跑后悄悄补一个新哈希，而是：保留原始预测文件，补记其哈希与不可变路径/对象版本；若原始文件已不可得，则把这次对比标记为“历史指标，不能独立复核”，再在固定条件下进行一次新的、可追溯的 A/B 评测。

最小验证关系可记为：

~~~text
manifest.artifacts.predictions.sha256
       = 对 predictions_run.jsonl 重新计算的 SHA-256
       ↓
metrics.json / failures.jsonl / release_decision.json
都能追溯到这一份确定的原始答卷
~~~

## 版本演进如何复核

是的，但版本迭代不是只靠两个 ID 就自动可见。它们是关联键；每个 run_id 还需要链接自己的 run_manifest.json、原始预测、指标、失败样本和决策文件，才能形成完整证据链：

~~~text
baseline_run_id: refund-eval-20260901-004
    └─ manifest（数据/prompt/model/evaluator/runtime/哈希）
    └─ predictions / metrics / failures / decision

run_id: refund-eval-20260908-010
    └─ manifest（同样的不可变引用）
    └─ predictions / metrics / failures / decision
    └─ baseline_run_id → refund-eval-20260901-004
~~~

## Day12 续｜离线通过后，线上到底监控什么？

离线 test 证明的是：在一份固定、已标注、无泄露的数据上，模型满足当时的验收门槛。它不能保证上线后仍然安全，因为线上会出现新模板、新来源、流量分布变化、服务降级，甚至日志/评测链路本身变化。

因此上线后不要只盯一个 accuracy（它通常还会因标签延迟而不能立即得到），而要把监控拆成四层：

| 层次 | 监控对象 | 能尽早发现什么 |
|---|---|---|
| 1. 输入与流量 | 请求量、来源/场景占比、文本长度、语言/模板、缺失率 | 数据分布或流量改变，即输入漂移 |
| 2. 输出与契约 | JSON/schema 合法率、unknown 占比、状态类别占比、evidence 可定位率 | prompt/模型/服务输出异常，或策略明显偏移 |
| 3. 业务风险与质量 | 延迟到达的人工金标、方向性错误率、人工复核拒绝率、投诉/纠错率 | 真正的任务质量和高风险误报是否恶化 |
| 4. 服务与观测链路 | p50/p95 延迟、超时/重试、模型版本、日志覆盖率、采样率 | 服务故障、版本漂移、监控数据本身失真 |

它们之间不是“任何一个上涨就立即认定模型坏了”，而是一条分诊链路：

~~~text
输入/流量异常？       → 先查数据或流量分布变化
输出/契约异常？       → 先查 prompt、模型版本、服务降级或解析链路
风险/人工质量恶化？  → 查真实模型质量，并按场景回溯失败样本
服务/日志异常？       → 先修复观测和服务；不要把坏数据当模型回归
~~~

例如，“已退款”占比从 40% 升到 65% 不是自动的模型回归信号：可能是某渠道当天本来就涌入了大量已退款工单；也可能是模型开始把“退款处理中”错报成“已退款”。前者主要是输入分布变化，后者是高风险质量问题。仅看类别占比无法区分，必须结合来源分布、模型版本、样本审计和延迟金标。

## 两个很像、但不同的指标

本题的 100 条全部来自“模型预测已退款”。其中 8 条人工金标为“退款处理中”，所以能直接计算的是：

~~~text
P(金标=退款处理中 | 模型预测=已退款) = 8 / 100 = 8%
~~~

它描述的是：**模型说“已退款”的 100 个案例中，抽样发现 8 个其实仍在处理中。**这可称为“已退款预测的高风险假阳性占比”，适合快速排查。

但发布门槛里定义的方向性错误率是：

~~~text
P(模型预测=已退款 | 金标=退款处理中)
= 真实退款处理中、但被模型说成已退款的数量
  ÷ 真实退款处理中样本总数
~~~

这里分母是“金标退款处理中”的全部样本；而当前抽样在标注前根本不知道哪些样本真实处理中，因此不能用 100 作这个指标的分母。

一个极端例子能说明差异：若线上只有 10 条真实“退款处理中”，其中 8 条被错报已退款，则方向性错误率是 8/10=80%；若线上有 1,000 条真实处理中，仍有同样 8 条错报，则是 8/1000=0.8%。两种场景都可能在“预测已退款抽样 100 条中发现 8 个真处理中”，但风险结论完全不同。

第 2 题你的回答方向正确：这 100 条证明当前确实发现了“退款处理中→已退款”的真实错例，值得触发风险排查。它最适合回答：

- 在模型预测为已退款的结果中，高风险误报是否已经出现、样本形态是什么；
- 这些错例是否集中在来源 A、某个模板、某个时间段或某类证据表达；
- 是否需要提高复核、降级或扩大金标抽样。

## RLHF 从零讲解（第 1 节：它要解决什么）

先给结论：**RLHF = Reinforcement Learning from Human Feedback，人类反馈强化学习。**它不是一个单独的模型结构，而是一套后训练流程：让已经会说话的 SFT 模型，进一步学会在多个“都不算错”的回答中，更倾向人类认为更有帮助、诚实、安全、符合风格的那个。

### 1. 为什么有了 SFT 还需要 RLHF？

SFT 的训练数据是“问题 → 标准答案”。例如：

~~~text
问题：退款多久到账？
示范答案：通常 3–5 个工作日到账；若超过时限请提供订单号以便查询。
~~~

它能教模型模仿示范，但现实中常常没有唯一标准答案。对于同一个问题，回答 A 和 B 都可能事实正确，但人更喜欢 B：更直接、更完整、不编造、风险更低。此时，与其要求标注员逐字写出“唯一正确答案”，更自然的是让人做比较：

~~~text
prompt：退款处理中代表已经退款了吗？
chosen（人更偏好）：不一定。处理中表示退款仍在处理，建议以退款明细或到账通知为准。
rejected（人不偏好）：是的，处理中就是已退款。
~~~

这类 chosen / rejected 的比较，就是人类反馈。RLHF 的目标是：让模型以后更常生成类似 chosen、少生成类似 rejected 的答案。

### 2. 经典 RLHF 的三步

~~~text
① SFT 模型
   学会基本任务与语言能力
          ↓
② 人类偏好数据 → Reward Model（RM，奖励模型）
   学会给“一个回答有多受人偏好”打分
          ↓
③ PPO 更新策略模型
   模型自己生成回答，RM 打分；高分回答的生成倾向被增强，
   同时由 KL 约束避免偏离原来的 SFT 模型过远
~~~

这三者的职责一定要分清：

- **SFT 模型**：初始的“会答题的学生”。
- **人类偏好数据**：裁判只需说 A 比 B 好，不必每次重写满分答案。
- **Reward Model**：把“人更喜欢 A 而非 B”的比较，学习成一个可自动打分的函数。它不是最终聊天模型。
- **PPO**：一种强化学习优化方法，利用奖励模型的分数更新最终聊天模型；它不是奖励模型，也不是偏好数据。

### 3. 用退款场景走一遍

设 SFT 模型被问：“退款处理中代表钱已经到账了吗？”

它生成两种候选回答：

~~~text
A：是，退款处理中代表钱已经到账。
B：不一定。退款处理中表示流程还未结束，应以到账通知或退款明细为准。
~~~

标注员偏好 B。积累很多这样的比较后，Reward Model 学到：B 的分数应高于 A。

接着 PPO 让当前模型继续生成回答；Reward Model 给分高的回答会让模型“下次更愿意这样说”，低分回答则让它“下次少这样说”。因此，PPO 阶段需要模型实际生成新回答，这一步通常称为 rollout。

### 4. 为什么不能只追求 Reward Model 的最高分？

因为 Reward Model 只是从有限的人类偏好中学出来的代理评分器，不是真实世界的绝对裁判。若模型一味钻奖励模型的空子，得到高分但对用户没有真正帮助，这叫 **reward hacking（奖励投机）**。例如模型学会无论什么问题都写很长、反复声明“我无法确认”、堆砌安全话术，可能骗过某些奖励模式，却没有解决问题。

所以经典 RLHF 会加 **KL 约束**：新模型不能为了追求奖励，和原来的 SFT 模型差得过远。你可以把它理解成“奖励是油门，KL 是方向盘和刹车”。后面讲 PPO 时会说明它如何进入目标函数。

### 5. 与你已经学过的 DPO 的关系

两者都使用偏好信息，但路径不同：

| 经典 RLHF + PPO | DPO |
|---|---|
| 先训练 Reward Model，再由 PPO 用奖励训练模型 | 直接用 chosen / rejected 更新模型 |
| 需要生成 rollout、奖励打分、策略优化 | 不需要显式 Reward Model，也不跑 PPO |
| 流程更复杂、成本与不稳定性更高 | 工程更简单，常适合离线偏好对 |

DPO 不是“不需要偏好数据”，PPO 也不是“比 DPO 更高级”。选择取决于反馈来源、是否要在线探索、是否有可靠奖励，以及工程成本。

这一节的验收只需能区分三件事：人类偏好数据负责提供比较；Reward Model 负责自动打分；PPO 负责依据打分更新最终模型。

是的，**DPO 有“不要偏离 reference model 太远”的 KL-regularized RL 理论来源**；但标准 DPO 的训练 loss 中，通常**没有像 PPO 那样显式写一项并逐步计算**“RM reward − β×KL”。它把这层约束折叠进了“policy 相对 reference 的 chosen/rejected 概率比”中。

先回顾 DPO 要学什么。每条训练样本是：

~~~text
(x, y⁺, y⁻)
x：prompt
y⁺：chosen，人偏好的回答
y⁻：rejected，人不偏好的回答
~~~

目标不是把 y⁺ 当作 SFT 的唯一标准答案去模仿，而是让 policy 对 y⁺ 的相对偏好高于 y⁻，并且这个“提高多少”是相对于冻结的 reference model 而言。标准 DPO loss 可写为：

~~~text
L_DPO = − log σ( β × [
  (log πθ(y⁺|x) − log πref(y⁺|x))
− (log πθ(y⁻|x) − log πref(y⁻|x))
])
~~~

读法如下：

- πθ：正在训练的 policy model；
- πref：冻结的 reference model，通常就是 SFT 模型的一份副本；
- 第一个括号：policy 相对 reference，有没有更倾向 chosen；
- 第二个括号：policy 相对 reference，有没有更倾向 rejected；
- 总体希望前者大、后者小，也就是让 chosen 相对 rejected 的优势变大；
- β：DPO 的温度/尺度参数，在其 KL-regularized RL 推导中对应控制“偏好优化”与“贴近 reference”取舍的量。

因此，DPO 和 PPO 的关系可以这样区分：

| 项目 | PPO-RLHF | DPO |
|---|---|---|
| 偏好信号 | Reward Model 给新 rollout 打分 | 固定 chosen/rejected 偏好对 |
| 核心优化 | RM reward − 显式 KL 惩罚 | 相对 reference 的 pairwise 偏好概率 |
| KL 是否显式计算 | 是，训练中直接监控/惩罚 | 基本 DPO loss 不单独计算 KL 项 |
| reference 的作用 | 计算 KL，限制 policy 漂移 | 出现在 loss 的 log-prob 比中，提供锚点 |
| 是否需要 RM / rollout | 需要 | 不需要 |

所以最准确的一句话是：**DPO 不是完全没有 KL 思想；它是从 KL 正则化的偏好优化问题推导而来，但标准 DPO 用 reference-relative 的偏好 loss 隐式实现这种约束，而不是在训练时额外加一项显式 KL loss。**

也要注意：DPO 的 β 不是简单照搬 PPO 中“β 越大/越小”的操作直觉。它会改变偏好 margin 的尺度，并与 reference 锚定相关；实际训练还受学习率、数据质量、epoch 等共同影响，应靠 chosen/rejected accuracy、KL/长度分布与独立评测一起调参。若有人在 DPO 上额外加入 SFT/NLL 或显式 KL，那是一个变体/辅助正则，不是最基本的 DPO 定义。

用退款例子：若 reference 原本把“处理中就是已退款”和“不一定”都给了相近概率，DPO 只要求 policy 相对 reference 更提高“不一定”的概率、并更降低错误回答的概率；它不会训练 Reward Model，也不会让 policy 先自由 rollout 后再用 RM 打分。

你记得的是 **margin（偏好间隔）**，很多讲解会把它记为 m。标准 DPO 确实有这个量，但它通常不是一个要单独设定的固定 m 超参数。

可以把刚才 loss 方括号里的量命名为：

~~~text
mθ(x, y⁺, y⁻)
= [log πθ(y⁺|x) − log πref(y⁺|x)]
  − [log πθ(y⁻|x) − log πref(y⁻|x)]
~~~

它表示：**当前 policy 相对 reference，对 chosen 的偏向，相比对 rejected 的偏向，拉开了多大间隔。**

于是标准 DPO loss 可简写为：

~~~text
L_DPO = −log σ(β × mθ)
~~~

- mθ 大：policy 相对 reference 更偏好 chosen、也更排斥 rejected；这是 DPO 希望看到的方向。
- mθ 小或为负：policy 没有充分偏向 chosen，甚至更偏向 rejected；loss 更大，梯度会推动它修正。
- mθ 是由当前 policy 的 log probability 算出来的，训练过程中不断变化，不是先指定一个常数。

你也可能见过“固定目标 margin”的写法；那通常是 **DPO 的变体**，而不是最基本 DPO。例如 SimPO 会引入一个固定的目标间隔 γ（有些资料也会把它泛称 m），形式近似：

~~~text
−log σ(β × [log πθ(y⁺|x) − log πθ(y⁻|x)] − γ)
~~~

这里 γ 才是人为设定的“希望 chosen 至少领先多少”的超参数；它和标准 DPO 中动态算出的 mθ 不是同一个东西。

所以一句话记忆：

~~~text
标准 DPO：有动态的 preference margin mθ；核心超参数是 β。
某些 margin-based 变体：还会额外有固定 target margin（常写 γ 或 m）。
~~~

刚才的小练习的答案也就清楚了：policy 更偏向 chosen 且更少偏向 rejected 时，mθ 会变大；DPO loss 希望 mθ 变大。

DPO 中 β 的核心作用是控制：**为了学会 chosen 优于 rejected，policy 允许偏离 reference model 多远。**它不是学习率，也不是固定 margin。

沿用刚才的简写：

~~~text
L_DPO = −log σ(β × mθ)

mθ = [log πθ(y⁺|x) − log πref(y⁺|x)]
   − [log πθ(y⁻|x) − log πref(y⁻|x)]
~~~

在标准 DPO 的 KL-regularized 推导约定下，β 对应 KL 正则的权重：

- **β 较大**：同样的“chosen 比 rejected 更受偏好”的置信程度，可以用更小的相对概率变化达到；policy 更贴近 reference，训练更保守，偏好改进也可能不够。
- **β 较小**：要把 loss 压低，需要拉开更大的 mθ；policy 更愿意远离 reference 来拟合偏好对，偏好学习更激进，但更易过拟合偏好数据、长度漂移或损伤通用能力。

这看起来容易和公式中“β 乘在 mθ 前面”冲突：β 大时局部梯度的数值尺度也会变大，但 sigmoid 会更快饱和；从 DPO 的整体最优解/理论解释看，**更大的 β 对应更强的 reference 锚定（更大的 KL 正则），而不是更激进的偏好偏移。**

与 PPO 对比：

| 训练法 | β 的直观含义 | β 变大后 |
|---|---|---|
| PPO 目标：reward − β·KL | 显式 KL 惩罚系数 | 更保守、更贴近 reference |
| 标准 DPO | 隐式 KL 正则对应的尺度参数 | 更保守、更贴近 reference |

但实际使用时必须先核验框架实现的公式和文档：少数实现可能使用了 β 的倒数或不同命名；不要只凭参数名跨项目迁移数值。

## 怎么调节训练

把 β 当作“偏好更新幅度的主旋钮”，学习率当作“每一步走多快的主旋钮”。不要看到过拟合就同时改 β、学习率、epoch，否则无法归因。

一个最小调参流程：

1. 固定数据切分、reference、最大长度、有效 batch、epoch 和学习率，只做 β 的小网格，例如从 0.01、0.03、0.05、0.1、0.2 中选适合当前任务的少数候选；这些只是起始搜索点，不是通用最优值。
2. 每个候选都在相同 valid/test 上比较，而不是只看训练 loss。至少看：
   - chosen/rejected 的偏好准确率；
   - policy 相对 reference 的 KL 或平均 log-ratio、回答长度和拒答率等分布漂移；
   - 原有关键能力与高风险门槛，例如退款处理中→已退款错误率。
3. 若偏好准确率提升很少、KL 极低、输出几乎等同 reference：β 可能过大，或训练总步数/学习率不足；先尝试适度减小 β，并保持其余变量不变。
4. 若训练偏好准确率很高，但 valid 退化、KL/长度快速增大、格式或高风险指标变差：β 可能过小，或 epoch/学习率过大；先增大 β，或在下一轮单独降低学习率/减少 epoch。
5. 选择“独立评测通过所有硬门槛、且漂移可接受”的最保守候选，而不是 DPO loss 最低或训练偏好准确率最高的候选。

## 回到 PPO：rollout 与 advantage 为什么需要？

DPO 直接在固定的 chosen/rejected 偏好对上训练；PPO 不同，它需要先让**当前 policy 自己生成新的回答**，再根据这些实际生成的回答更新自己。

~~~text
prompt
  ↓
当前 policy 生成回答（rollout）
  ↓
Reward Model 打分 + 计算与 reference 的 KL 代价
  ↓
得到该 rollout 的总回报
  ↓
用 advantage 判断“这次回答比预期好还是差”
  ↓
PPO 小步更新 policy
~~~

- **rollout**：当前 policy 对一批 prompt 实际采样出的完整回答（以及每个 token 的概率、log-prob 等训练记录）。没有 rollout，就没有 PPO 要学习的“当前策略真实会产生什么”。
- **reward / return**：RM 分数扣掉 KL 代价后的回报信号。
- **advantage（优势）**：不是只问“得分高不高”，而是问“它比这个 prompt 下原本可预期的水平好多少”。概念上可记为：

~~~text
advantage = 实际获得的回报 − 价值模型预估的平均回报
~~~

若 advantage 为正，PPO 增加这条 rollout 中相应 token 的生成倾向；为负则降低。价值模型（value model/critic）用于估计“原本预期能拿多少分”，从而减少不同 prompt 难度带来的更新噪声。

退款例子：

~~~text
prompt：退款处理中代表到账了吗？
rollout A：不一定，应以到账通知为准。
rollout B：是，处理中就是到账。
~~~

若 RM 扣除 KL 后认为 A 明显优于当前预期，则 A 的 advantage 为正，PPO 会更倾向生成 A 类回答；B 的 advantage 为负，则降低这类回答的倾向。注意，这仍依赖 RM 可信，不能替代独立评测。

小练习：两个 prompt 的 RM 回报分别是 8 分和 6 分；价值模型对它们的预期回报分别是 7 分和 2 分。哪一个 rollout 的 advantage 更大？PPO 更应该增强哪一个 rollout 的生成倾向？

计算是：

~~~text
第一个：8 − 7 = 1
第二个：6 − 2 = 4
~~~

关键点在于：第二个的**绝对回报**其实更低（6 < 8），但它比这个 prompt 下原本的预期好得更多（+4 > +1）。所以 advantage 学的是“超出预期多少”，而不是机械偏爱 RM 分最高的样本。

接下来还有一个风险：既然第二个 advantage 很大，能否一次就把它的概率大幅提高？不能。这样 policy 很容易一步偏离旧 policy 太远，训练不稳定，也更容易利用 RM 的漏洞。

PPO 为此记录每个 token 在更新前后的概率比：

~~~text
r = π_new(token) / π_old(token)
~~~

若 `r = 1`，说明这个 token 的概率没变；`r = 1.1` 表示提高了约 10%。PPO 会对这个变化设一个可接受范围，例如 ε=0.2，即大致限制在 `[0.8, 1.2]`。对于正 advantage 的 rollout，概率提高到 1.2 以内会得到优化收益；若已经提高到 1.3，PPO 会把用于目标函数的比例截为 1.2，不再因为“继续抬高”而提供额外奖励。这就是 clipping（裁剪）：它不是禁止参数继续变化的绝对硬墙，但会消除越界方向的优化激励，让一次更新别走太远。

概念上，PPO 的 policy 项可写为：

~~~text
min(r × A, clip(r, 1−ε, 1+ε) × A)
~~~

其中 A 就是 advantage。正 A 鼓励提高该回答/token 的概率，负 A 鼓励降低；clip 负责限制这次相对旧 policy 的变化幅度。reference model 的 KL 则是另一层“不要偏离 SFT 太远”的约束。

小题：设 ε=0.2，某个 **advantage 为正** 的 token 从旧 policy 到新 policy 的概率比 `r=1.3`。PPO 在目标函数里会按 `1.3` 还是 `1.2` 计算这次概率提升？为什么？

你说得对：如果不把张量、输入输出和 `backward()` 连起来，PPO 的公式几乎没有可读性。先不看完整工程，先看一次 **PPO policy 更新真正做的事**。下面是接近 PyTorch 的最小核心；它假设 rollout 已经采好。

~~~python
import torch
import torch.nn.functional as F

# rollout 阶段保存下来的数据；B=batch，T=生成回答的 token 数
generated_ids = batch["generated_ids"]       # [B, T]，当前 policy 当时生成的 token id
old_logp = batch["old_logp"]                 # [B, T]，生成当时 old policy 对这些 token 的 log-prob
advantages = batch["advantages"]             # [B, T] 或 [B, 1]，例如 return - value

# 训练阶段：拿“同一批 prompt + 同一条已生成回答”重新过正在更新的 policy
logits = policy(input_ids, attention_mask).logits  # [B, sequence_length, vocab_size]
response_logits = select_response_positions(logits) # 对齐到生成 token 的前一位置，[B, T, V]
log_probs = F.log_softmax(response_logits, dim=-1)

# 从全词表概率中，只取 rollout 当时实际选中的 token 的 log-prob
new_logp = log_probs.gather(
    dim=-1, index=generated_ids.unsqueeze(-1)
).squeeze(-1)                                      # [B, T]

# 概率比。log 概率相减后 exp，数值更稳定
ratio = torch.exp(new_logp - old_logp)              # [B, T]

clip_eps = 0.2
unclipped = ratio * advantages
clipped = torch.clamp(ratio, 1 - clip_eps, 1 + clip_eps) * advantages
policy_loss = -torch.min(unclipped, clipped).mean()

optimizer.zero_grad()
policy_loss.backward()      # 梯度回传，只更新 policy 参数
optimizer.step()
~~~

把它逐行翻译成人话：

- `generated_ids` 是 rollout 已经生成出来的回答。例如回答被 token 化后是 `["不", "一", "定"]` 对应的 id。**训练时不会重新采样一个新答案**，而是评估这条既有答案在新 policy 下的概率。
- `old_logp` 是“生成这条答案那一刻”的旧 policy 概率快照，必须在 rollout 时存下来，且不参与梯度。
- `new_logp` 是参数已经开始变化的 policy，对**同一个 token**给出的新概率。
- `ratio = exp(new_logp - old_logp)` 就是 `p_new / p_old`。初始时 policy 是 old policy 的副本，故 ratio 接近 1；在同一批 rollout 上做多轮更新后，ratio 才会偏离 1。
- `policy_loss.backward()` 会让正 advantage 的 token 概率上升、负 advantage 的 token 概率下降；但 `torch.clamp` 让 ratio 越过区间后不再获得额外优化收益。

举一个只有一个 token 的数字例子。若它的 `advantage=4`，旧概率是 `0.10`，更新后变成 `0.13`：

~~~text
ratio = 0.13 / 0.10 = 1.3
unclipped = 1.3 × 4 = 5.2
clipped   = 1.2 × 4 = 4.8       # ε = 0.2
min(...)  = 4.8
~~~

因此 loss 只把“最多提高约 20%”当作有效收益，避免继续把它从 0.13 推到更高。实现上 `min` 对正 advantage 自动选 4.8；对负 advantage 则会自动防止概率被过度压低——不用另写 if/else。

## rollout 从哪里来？

上面 `batch` 不是凭空出现，真实流程大致如下：

~~~python
with torch.no_grad():
    # 1. 当前 policy 采样回答；同时记录每个生成 token 的 old_logp
    generated_ids, old_logp = sample_with_logprobs(old_policy, prompts)

    # 2. RM 为“prompt + 完整回答”打一个标量分数
    rm_reward = reward_model(prompts, generated_ids)       # [B]

    # 3. critic/value 给预期回报；可配合 GAE 得到逐 token advantage
    values = value_model(prompts, generated_ids)           # [B, T]
    returns, advantages = compute_gae(rm_reward, values)

    # 4. 存成训练 batch；old_logp、advantages、returns 都 detach，不回传梯度
    batch = {
        "generated_ids": generated_ids,
        "old_logp": old_logp,
        "advantages": advantages,
        "returns": returns,
    }
~~~

完整 RLHF 的 loss 通常不只上面的 `policy_loss`，还会加两项：

~~~python
loss = policy_loss + vf_coef * value_loss + kl_coef * kl_penalty
~~~

- `value_loss`：让 value model 更接近实际 `returns`，下次才能更准确地算 advantage；
- `kl_penalty`：把 policy 与冻结的 `reference_model` 拉近。工程上常在相同 token 上用 `new_logp - ref_logp` 的采样近似来监控/惩罚 KL；若要精确 token-level KL，则对整个词表分布求和。

所以要记住两个不同的“旧模型”：

| 名称 | 生命周期 | 在代码里做什么 |
|---|---|---|
| `old_policy` | 每收集一批 rollout 后刷新一次 | 提供 `old_logp`，用于 PPO ratio / clip |
| `reference_model` | 通常从 SFT 后一直冻结 | 提供 `ref_logp`，用于 KL 约束 |

它们开始时可能是同一份 SFT 权重，但作用不同；绝不能把 `old_logp` 和 `ref_logp` 混为一谈。

好，下面看一个 **Hugging Face + TRL 的 PPO 训练骨架**。重点不是现在就跑它，而是理解：你写什么，TRL 在 `step()` 里替你做了什么。

先说明版本边界：TRL 的 `PPOTrainer` 在不同大版本中构造参数有所变化；下面采用教程里常见的经典调用形态，便于把数据流看清。换到具体版本时，应以该版本 API 文档为准，但 `generate → reward → step` 的主链不变。

~~~python
import torch
from datasets import Dataset
from transformers import AutoTokenizer, pipeline
from trl import AutoModelForCausalLMWithValueHead, PPOConfig, PPOTrainer

base_model = "your-sft-checkpoint"
rm_checkpoint = "your-reward-model-checkpoint"

# 1. policy：从 SFT 初始化；ValueHead 是给每个位置估计 value 的额外小头
policy = AutoModelForCausalLMWithValueHead.from_pretrained(base_model)

# 2. reference：同一份 SFT 权重的冻结副本，专门用于 KL 约束
ref_policy = AutoModelForCausalLMWithValueHead.from_pretrained(base_model)
ref_policy.eval()
for p in ref_policy.parameters():
    p.requires_grad_(False)

tokenizer = AutoTokenizer.from_pretrained(base_model)
tokenizer.pad_token = tokenizer.eos_token

# 3. PPO 的关键配置；学习率、clip 与 KL 系数是不同旋钮
config = PPOConfig(
    learning_rate=1e-6,
    batch_size=8,
    mini_batch_size=2,
    ppo_epochs=4,       # 同一批 rollout 重复更新 4 轮，ratio 因此会偏离 1
    cliprange=0.2,      # PPO clip ε
    init_kl_coef=0.05,  # reference KL 的初始系数
)

# 4. 数据集只提供 prompt；PPO 的回答不是预先给定的 chosen/rejected
train_data = Dataset.from_dict({
    "prompt": [
        "退款处理中代表已经到账了吗？",
        "订单取消后退款多久到账？",
    ]
})

def tokenize_prompt(row):
    row["input_ids"] = tokenizer(row["prompt"], add_special_tokens=False)["input_ids"]
    return row

train_data = train_data.map(tokenize_prompt)

# 5. RM：输入 prompt + policy 实际生成的完整回答，输出一个标量分数
# 这里假设该 checkpoint 是已训练好的 sequence-classification Reward Model。
reward_pipe = pipeline(
    task="text-classification",
    model=rm_checkpoint,
    tokenizer=rm_checkpoint,
    device=0,  # 没有 GPU 时应改成 -1
)

trainer = PPOTrainer(
    config=config,
    model=policy,
    ref_model=ref_policy,
    tokenizer=tokenizer,
    dataset=train_data,
)

# 6. 训练主循环：每一轮只需要看懂下面三步
generation_kwargs = {
    "do_sample": True,
    "top_p": 0.9,
    "max_new_tokens": 64,
    "pad_token_id": tokenizer.eos_token_id,
}

for batch in trainer.dataloader:
    # A. rollout：policy 根据 prompt 新生成答案。
    #    结果是 token tensor，不是人工 chosen/rejected。
    query_tensors = batch["input_ids"]
    response_tensors = trainer.generate(
        query_tensors, return_prompt=False, **generation_kwargs
    )

    # B. reward：拼回「prompt + 回答」，让冻结 RM 逐条打分。
    query_texts = tokenizer.batch_decode(query_tensors, skip_special_tokens=True)
    response_texts = tokenizer.batch_decode(response_tensors, skip_special_tokens=True)
    rm_inputs = [q + r for q, r in zip(query_texts, response_texts)]
    scores = reward_pipe(rm_inputs)
    rewards = [torch.tensor(x["score"], device=policy.pretrained_model.device)
               for x in scores]

    # C. PPO update：这一个调用内部计算 log-prob、ratio、clip、KL、
    #    value loss，随后 backward() 和 optimizer.step()。
    stats = trainer.step(query_tensors, response_tensors, rewards)

    # 训练时应记录，而不是只看 reward：
    print({
        "mean_reward": torch.stack(rewards).mean().item(),
        "objective/kl": stats.get("objective/kl"),
        "ppo/loss/policy": stats.get("ppo/loss/policy"),
        "ppo/loss/value": stats.get("ppo/loss/value"),
    })
~~~

这段代码可以压缩成下面这张“变量去向表”：

| 变量 | 谁产生 | 含义 | 交给谁 |
|---|---|---|---|
| `query_tensors` | dataset | prompt 的 token id | `generate`、`step` |
| `response_tensors` | 当前 policy | 本轮 rollout 的回答 token id | RM、`step` |
| `rewards` | 冻结 RM | 每条完整回答的偏好分数 | `step` |
| `stats` | TRL | KL、policy loss、value loss 等训练证据 | 日志/告警/调参 |

最容易误解的是 C：`trainer.step(...)` **不是把 RM 分数当标签做 SFT**。它内部大致做了我们上一条中展开的事情：

~~~text
用 rollout 时的 policy 保存 old_logp
同一条 response 在更新中的 policy 下重算 new_logp
ratio = exp(new_logp - old_logp)
用 reward 与 value 计算 advantage
用 clipped PPO objective 更新 policy + value head
再用 reference 的 log-prob 计算/控制 KL
~~~

也就是说，PPO 真正的训练数据在每轮会变成：

~~~text
(prompt tokens, 当前 policy 生成的 response tokens, RM reward, old_logp, ref_logp, values)
~~~

而 DPO 的训练数据是固定的：

~~~text
(prompt, chosen response, rejected response)
~~~

工程上你至少需要检查四件事，否则脚本“能跑”也不等于训练有效：

1. `reward_pipe` 的 `score` 方向是否正确：高分必须代表更符合人类偏好；有的 RM 输出的是多个类别 logit，不能直接拿错一个字段当 reward。
2. `response_tensors` 是否只包含新生成回答、prompt/response 拼接和 padding 是否对齐；错一位 token，log-prob、KL 都会错。
3. `objective/kl`、回答长度、拒答率、格式/安全指标是否持续上升或漂移；不能只看 `mean_reward`。
4. RM 和独立评测集是否分离；RM 分升高只能说明更会迎合 RM，不足以说明线上更好。

你问得非常准确，前面必须纠正一个关键点：**reference model 不会针对同一批 prompt 再生成一份回答。**每个 prompt 只由当时的 policy 采样出一条 response；随后 policy、reference、value/RM 都围绕这条**固定 response**计算各自的量。下面按三个问题拆开。

## 1. Reward Model 是否要训练？如何训练？

经典 RLHF-PPO 中，通常要先训练一个 RM；它**不是 DPO**。两者都能用偏好对数据，但训练对象与 loss 不同。

一条 RM 训练样本是：

~~~text
(prompt x, 人更偏好的回答 y_win, 人不偏好的回答 y_lose)
~~~

RM 是“语言模型 backbone + 一个标量打分头”。它对完整序列 `x + y` 输出一个实数：

~~~text
rφ(x, y) ∈ R
~~~

训练目标只要求赢的回答分更高，常见 Bradley–Terry pairwise loss：

~~~python
score_win  = reward_model(prompt, chosen)    # [B]
score_lose = reward_model(prompt, rejected)  # [B]
rm_loss = -F.logsigmoid(score_win - score_lose).mean()

optimizer.zero_grad()
rm_loss.backward()
optimizer.step()
~~~

若 `score_win=3`、`score_lose=1`，差为正，loss 较小；若反过来，loss 大，梯度会推高 chosen 的分数、压低 rejected 的分数。训练完成后，PPO 阶段通常将 RM **冻结**，它只负责为 policy 新生成的回答给 reward，不再更新。

与 DPO 的区别：

| 方法 | 用偏好对训练谁 | 是否显式得到一个 RM |
|---|---|---|
| RM 训练 | 标量打分模型 `rφ(x,y)` | 是 |
| DPO | policy `πθ(y|x)` | 否 |

现实中也可以接入已有的可靠 reward/规则/可验证器，而不自训 RM；但若奖励来自主观人类偏好，经典路线就是先用偏好对训练 RM。

## 2. Value head 预估什么，如何训练？

Value head 不是预测“答案好不好”的最终 RM 分，而是预测：**在当前 token 位置、继续按当前 policy 生成，未来预计能获得多少总回报。**

backbone 在每个位置输出 hidden state `h_t`，value head 很小，通常就是线性层：

~~~python
values = value_head(hidden_states).squeeze(-1)   # [B, L]
# Vψ(s_t)：当前位置 s_t 的预期未来回报
~~~

这里 `L = prompt 长度 + response 长度`；实际只对 response 的 token 位置计算 loss。

它的监督信号不是人工标注，而是当前 rollout 后算出的 **return**。简化到整条回答时：

~~~text
return = RM(prompt, response) − KL 代价
advantage = return − value 预估
~~~

value loss 就是回归：

~~~python
# returns 来自当前 rollout 的实际 reward / GAE，不要对它回传梯度
value_loss = 0.5 * ((values_on_response - returns.detach()) ** 2).mean()
~~~

因此是一个自举循环：初期 value 估得不准；rollout 得到实际 return 后，value head 学着逼近它；下一批它就能更好地给 advantage 提供基线，降低 policy 更新的方差。很多 PPO 实现还对 value 更新做 clipping，防止 critic 一步跳太远。

## 3. 从 `[B, L, V]` 到 new logp、loss 与更新：完整一条链

先统一符号：

~~~text
B：batch size
Q：prompt token 数
T：response token 数
L = Q + T
V：词表大小
input_ids = [prompt tokens | policy 采样的 response tokens]，形状 [B, L]
~~~

真正的数据流是：

~~~text
(1) policy 采样 response y                         # 唯一的“生成”
                 ↓
    固定 full_ids=[x|y]
       ↙          ↓             ↘
 policy(old)   reference(frozen)   RM(frozen)
 old_logp      ref_logp            terminal RM reward
 values
       ↓
 returns / advantages
       ↓
 policy(current) 对同一 full_ids 重算 new_logp
       ↓
 PPO policy loss + value loss
       ↓
 backward() / optimizer.step()    # 只更新 policy + value head
~~~

注意：reference 做一次前向得到 `[B,L,V]`，但它**没有调用 generate**；它只是问：“对于 policy 已选定的每个 token，我给它多大概率？”

### A. rollout 阶段：谁产出什么

~~~python
with torch.no_grad():
    # 唯一生成回答的一步
    response_ids = policy.generate(prompt_ids, do_sample=True)  # [B, T]
    full_ids = torch.cat([prompt_ids, response_ids], dim=1)     # [B, L]

    # 这两个模型都读取相同 full_ids，输出都可能含 logits [B,L,V]
    old_out = policy(full_ids)        # 采样时 policy 的参数快照
    ref_out = ref_policy(full_ids)    # 冻结的 SFT reference

    old_logp = selected_response_logps(old_out.logits, full_ids, Q, T) # [B,T]
    ref_logp = selected_response_logps(ref_out.logits, full_ids, Q, T) # [B,T]
    old_values = old_out.value[:, Q-1:Q-1+T]                          # [B,T]

    rm_reward = reward_model(full_ids).score  # [B]，完整回答的一个标量分
~~~

这里的 `old_out` 不是另一个永久 `old_policy` 实例；通常是“PPO 对这一批 rollout 开始更新前的 policy”。框架把它的 `old_logp` 存成无梯度快照。在同一批数据上做多次 `ppo_epoch` 更新时，当前 policy 已变，才需要与这个快照比较。

### B. `[B,L,V]` 如何变成 response 的 logp `[B,T]`

语言模型有一个右移关系：位置 `i` 的 logits 预测 `input_ids[i+1]`。

~~~python
def selected_response_logps(logits, full_ids, prompt_len, response_len):
    # logits[:, i, :] 是对 full_ids[:, i+1] 的 V 个词的分布
    log_probs = torch.log_softmax(logits[:, :-1, :], dim=-1)  # [B, L-1, V]
    next_tokens = full_ids[:, 1:]                             # [B, L-1]

    # response 第一个 token y_0 由 prompt 最后一个位置 Q-1 的 logits 预测
    start = prompt_len - 1
    token_logp = log_probs.gather(
        dim=-1, index=next_tokens.unsqueeze(-1)
    ).squeeze(-1)                                             # [B, L-1]
    return token_logp[:, start : start + response_len]        # [B, T]
~~~

所以 `new_logp` 并不是 policy response 同某个“新回答”比较得到的。它是：**当前参数的 policy 对同一条已采样 response 中每个实际 token 的 log probability。**

在第 k 次 mini-batch 更新时：

~~~python
current_out = policy(full_ids)
new_logp = selected_response_logps(current_out.logits, full_ids, Q, T)  # [B,T]
ratio = torch.exp(new_logp - old_logp)                                  # [B,T]
~~~

初始第一次时 current policy 与采样时相同，`new_logp ≈ old_logp`、`ratio≈1`；做过一次 `optimizer.step()` 后，再过同一条 `full_ids`，才会得到不同的 `new_logp` 和 ratio。

### C. RM、reference、value 如何变成 advantage

最简化的 token 级写法是把 RM 的整句分数放在最后一个有效 response token；每个 token 再扣除“当前 policy 比 reference 更偏向该 token”的 KL 近似：

~~~python
kl_sample = old_logp - ref_logp                   # [B,T]，采样 KL 近似
token_rewards = -kl_coef * kl_sample               # [B,T]
token_rewards[:, -1] += rm_reward                  # [B] 加到回答末尾

returns, advantages = compute_gae(
    token_rewards, old_values, gamma=1.0, lam=0.95
)                                                   # 都是 [B,T]
advantages = normalize_over_valid_tokens(advantages)
~~~

`compute_gae` 由训练框架实现，核心是从后向前把“实际 token reward + 后续 value”累积成 return，并以 `return - value` 得到 advantage。不同实现对 KL 是直接加在 reward 中、还是以单独 loss 计入，细节会不同；但 `RM 回报`、`reference KL`、`value baseline` 三者的职责不变。

### D. current policy 怎样得到最终 loss 并更新

~~~python
# 对固定 full_ids 再次前向；这里保留梯度
out = policy(full_ids)
new_logp = selected_response_logps(out.logits, full_ids, Q, T)  # [B,T]
new_values = out.value[:, Q-1:Q-1+T]                            # [B,T]

ratio = torch.exp(new_logp - old_logp)
eps = 0.2
policy_objective = torch.minimum(
    ratio * advantages,
    torch.clamp(ratio, 1-eps, 1+eps) * advantages,
)
policy_loss = -masked_mean(policy_objective, response_mask)

loss.backward()
~~~

产出责任可以这样记：

| 量 | 谁产生 | 是否更新 |
|---|---|---|
| `response_ids` | policy 的 `generate` | 生成时不回传梯度 |
| `rm_reward [B]` | 冻结 RM | 不更新 |
| `ref_logp [B,T]` | 冻结 reference 对同一 `full_ids` 前向 | 不更新 |
| `old_logp`、`old_values` | rollout 当刻的 policy 快照 | 存档、无梯度 |
| `new_logp`、`new_values` | 当前 policy 对同一 `full_ids` 再前向 | 有梯度 |
| `returns`、`advantages` | GAE 逻辑，由 reward、KL、old value 算出 | 无梯度目标 |
| `loss` | PPO loss + value loss 逻辑 | 驱动更新 policy/value head |

~~~text
full_ids = [prompt tokens | y1 | y2]
~~~

## 1. RM 是回归模型吗？如何训练？

可以把 RM 看成“**输出标量分数的排序/偏好模型**”，但它不是普通的“输入一个样本、拟合一个固定绝对分数标签”的回归。人类通常只提供相对标签：同一 prompt 下，A 比 B 好。

训练时一条偏好数据有两个完整序列：

~~~text
(x, y_win)   # chosen
(x, y_lose)  # rejected
~~~

同一个 RM 对两条序列**分别**前向，给两个标量：

~~~python
s_win  = rm(concat(prompt, chosen)).score    # [B]
s_lose = rm(concat(prompt, rejected)).score  # [B]
loss = -F.logsigmoid(s_win - s_lose).mean()
~~~

它学的是 `s_win > s_lose`，而不是要求 chosen 必须等于某个“8.5 分”的人工绝对标签。训练完成后，对于 PPO 新生成的一条回答，只需输入一条 `prompt + response`，RM 就会输出一个标量 reward。

因此：

- 训练 RM 时：每个偏好对要算 chosen 和 rejected 两次分数，再用差值训练；
- PPO 使用 RM 时：每条 policy 新生成的 response 只需算一次分数；
- RM 一般在 PPO 前训练好并冻结；PPO 不用 DPO loss 训练 RM。

## 2. value head 在哪个模型上？`values_on_response` 从哪里来？

在经典 RLHF-PPO / TRL 的常见实现里，value head 挂在 **正在训练的 policy 的 Transformer backbone** 上。它不是 reference，也不是 RM。

~~~text
同一套 policy Transformer hidden states
       ├─ LM head    → logits，决定下一个 token 的概率
       └─ value head → value，预估未来回报
~~~

简化代码就是：

~~~python
hidden_states = policy_backbone(full_ids)         # [B, L, H]
logits = lm_head(hidden_states)                   # [B, L, V]
all_values = value_head(hidden_states).squeeze(-1) # [B, L]
~~~

`all_values[b, i]` 的含义是：看到第 `i` 个 token 为止，在这个状态下继续生成，预计还能得到多少总回报。

对回答 token，我们实际要的是每一步**生成下一个回答 token 前**的 value。语言模型在“prompt 最后一个 token”的位置，正好要预测回答第一个 token `y1`。所以取：

~~~python
# 切片右端不包含；得到恰好 T 个数
values_on_response = all_values[:, prompt_len - 1 : prompt_len - 1 + response_len]
# 形状 [B, T]
~~~

若回答为 `y1, y2`，这两个数可以读作：

~~~text
values_on_response[:, 0]：在生成 y1 之前，对“y1 + y2 之后总回报”的预测
values_on_response[:, 1]：已生成 y1、在生成 y2 之前，对“y2 之后总回报”的预测
~~~

你看到的 `Q-1` 乱码只是平台把方括号误当成 issue 引用；原意就是上面的 `prompt_len - 1`。

有的系统会把 critic 做成与 policy 完全独立的模型；但核心语义不变：它输出每个生成位置的 value。在 TRL 的 `AutoModelForCausalLMWithValueHead` 形式中，通常是 policy backbone 共享、上面多一个 value head。PPO 的优化器会更新 shared policy backbone、LM head 和 value head；reference/RM 不更新。

## 3. 为什么 value loss 是平方误差？

value head 要回答的是一个数值预测问题：

~~~text
当前预测值：V(s_t) = values_on_response
事后观察到的目标：G_t = return
~~~

因此最直接的损失就是“预测减目标”的平方：

~~~python
error = values_on_response - returns.detach()
value_loss = 0.5 * (error ** 2).mean()
~~~

它并不神秘，就是回归里的 MSE：

- 若当前 value 预测 3，实际 return 是 5，误差为 -2；训练会把 value 往上推；
- 若当前 value 预测 8，实际 return 是 5，误差为 +3；训练会把 value 往下推；
- 平方让“大错”惩罚更大；前面的 `0.5` 只是方便求导，`d(0.5 × error²)/d(value) = error`。

`detach()` 很重要：`returns` 是这一轮 rollout 计算出的**固定教学答案**，critic 只能调整自己的 `values` 去追它，不能经由梯度反过来修改这个目标。

注意：这里的 return 不是“外部人工标注的真值”，而是这次 rollout 的 reward/KL 加上后续回报算出的训练目标。因此 value head 一开始不准是正常的，它随 rollout 逐渐学会当前 policy 的平均表现。

## 4. 为什么 response 要“采样”而不是总选概率最大的 token？

因为 PPO 优化的对象是一个随机策略 `π(token | prefix)`，而不是一个固定贪心程序。采样有三个目的：

1. **探索**：若永远 argmax，policy 不会尝试低一些但潜在更优的回答，RM 也没机会给那些路径高分；
2. **匹配训练目标**：PPO 的 `old_logp`、ratio 和期望 reward 都定义在 policy 实际采到的动作上；
3. **多样性**：同一 prompt 得到不同回答，RM 才能告诉 policy 哪些生成模式值得增加概率。

实践里通常用温度、top-p/top-k 控制采样，防止探索得过于随机。部署推理可以用不同策略（例如低温或 greedy）；PPO rollout 的采样设置则是训练契约的一部分。

## 5. `compute_gae`：先只理解它在做什么

GAE（Generalized Advantage Estimation）不是另一种模型；它是一个**纯计算函数**。输入：每一步 reward 和当前 value 预测；输出：

~~~text
advantages：这一步比当时预期好/坏多少，用于 policy loss
returns：critic 这一步应该回归到的目标，用于 value loss
~~~

先看不用 GAE 的最简单直觉：

~~~text
advantage = 实际后续总回报 − 当前 value 预估
return = 实际后续总回报
~~~

GAE 是把“只看最终整句分”改成“从后往前平滑地归因给每个 token”，以降低方差。它使用的局部误差叫 TD residual：

~~~text
delta_t = reward_t + gamma × V(next_state) − V(current_state)
~~~

并从回答末尾往前累计：

~~~text
A_t = delta_t + gamma × lambda × A_(t+1)
return_t = A_t + V(current_state)
~~~

`gamma` 通常衡量未来回报折扣；文本回答通常取 1 或接近 1。`lambda` 是平滑强度：接近 1 更充分使用完整序列回报，较小则更多依赖局部 value，方差更低但偏差可能更大。

### 两 token 数值例子

假设 `y1, y2` 两个位置的 value 预测是：

~~~text
V1 = 3.0    # 生成 y1 前的预测
V2 = 4.0    # 生成 y2 前的预测
终止后的 V3 = 0
~~~

KL 代价和 RM 分组合后，设 token reward 为：

~~~text
r1 = -0.1             # y1 的 KL 代价
r2 = 4.9              # y2 的 KL 代价 + RM 的整句奖励 5.0
~~~

取 `gamma=1`、`lambda=0.95`：

~~~text
delta2 = r2 + V3 − V2 = 4.9 + 0 − 4.0 = 0.9
A2 = delta2 = 0.9
return2 = A2 + V2 = 4.9

delta1 = r1 + V2 − V1 = -0.1 + 4.0 − 3.0 = 0.9
A1 = delta1 + 0.95 × A2 = 0.9 + 0.95 × 0.9 = 1.755
return1 = A1 + V1 = 4.755
~~~

解释：`y2` 位置实际得到 4.9，而预期 4.0，故它的 advantage 为正；`y1` 虽只直接承担 -0.1 的 KL，但它通向了一个最终高回报回答，所以也分到正 advantage。`compute_gae` 做的就是这种从后向前的累积；代码只是一个倒序循环。

~~~python
def compute_gae(rewards, old_values, gamma=1.0, lam=0.95):
    # rewards / old_values: [B, T]；此处省略 padding mask
    advantages = torch.zeros_like(rewards)
    next_advantage = torch.zeros(rewards.size(0), device=rewards.device)
    next_value = torch.zeros_like(next_advantage)  # 序列末尾 value = 0

    for t in reversed(range(rewards.size(1))):
        delta = rewards[:, t] + gamma * next_value - old_values[:, t]
        next_advantage = delta + gamma * lam * next_advantage
        advantages[:, t] = next_advantage
        next_value = old_values[:, t]

    returns = advantages + old_values
    return returns, advantages
~~~

真实工程会处理 EOS、不同长度、padding mask、value clipping、advantage 标准化；但不会改变上面这条因果链。

## 6. 同一批 response 会不会反复迭代？谁在变？

**是，但只在有限的 PPO 更新窗口内反复用。**标准节奏如下：

~~~text
第 n 轮：
  a. 用当前 policy 采一批新 response；保存 old_logp / old_values。
  b. 固定这批 full_ids，切成 mini-batch，做 K 个 PPO epoch。
     每次 optimizer.step() 后，policy 参数和 value head 参数改变。
     对同一 full_ids 重算，故 new_logp / new_values 随之改变。
  c. K 轮结束，丢弃该 rollout batch；用更新后的 policy 重新采下一批新 response。
~~~

所以不是拿第一批回答无限训练；那会严重过拟合且偏离 on-policy。

同一 `full_ids` 之中：prompt token 和 response token **不变**。改变的是 policy/value head 的参数 `θ`。因此：

~~~text
old_logp, old_values：参数 θ_old 下、rollout 时的无梯度快照
new_logp, new_values：参数 θ_current 下、每个 PPO mini-batch 前向重新计算的可求导结果
ref_logp：冻结参数 θ_ref 下，对同一 full_ids 的固定结果
~~~

第一次进入 PPO update 且还没执行过 `optimizer.step()` 时，`θ_current = θ_old`，故 new 和 old 几乎相同；第一次更新之后，二者开始不同。正是这种差异产生 `ratio = exp(new_logp - old_logp)`，PPO clipping 才能约束“一批数据上不要走得太远”。

一张最终的“谁动、谁不动”表：

| 组件或量 | rollout 内是否变化 | PPO 更新中是否变化 |
|---|---:|---:|
| `full_ids` / response tokens | 否 | 否 |
| RM 参数 | 否 | 否（冻结） |
| reference 参数与 `ref_logp` | 否 | 否（冻结） |
| `old_logp` / `old_values` | 否（快照） | 否（快照） |
| policy 参数 | 采样后先固定 | 是 |
| value head 参数 | 采样后先固定 | 是 |
| `new_logp` / `new_values` | 每次前向重算 | 随参数变化 |

你最后一条可以概括为：**对，同一 `full_ids` 上，old 是更新前存档，new 是更新后的/更新中的当前 policy 的重新输出；变化的是 policy 和 value head 参数，而不是那条 response。**

## 1. 什么是 on-policy？

`policy` 就是当前用于生成回答的模型分布 `πθ`。**on-policy** 的意思是：用来训练 policy 的 rollout，必须由当前 policy（或与它足够接近的旧版本）自己生成。

在 PPO 的一轮中：

~~~text
当前参数 θ_old 的 policy
  → 采样 prompt 的 response，保存 old_logp / old_values
  → 用这批 response 做少量 PPO 更新
  → 得到 θ_new
  → 重新用 θ_new 采下一批 response
~~~

为什么不能长期拿很早以前模型生成的回答反复训练？因为那些回答来自旧分布 `π_old`，已经不能代表当前模型 `π_current` 实际会怎样说话；此时 reward、advantage 和梯度的含义都会越来越不准。

PPO 不是“绝对严格的一次 rollout 只更新一步”的 on-policy：它会将同一批数据复用少量 `ppo_epochs`，以提高样本利用率。但每次更新都通过：

~~~text
ratio = exp(new_logp - old_logp)
clip(ratio, 1-eps, 1+eps)
~~~

限制 current policy 不要偏离采样时的 old policy 太远。因此更准确地说，PPO 是**近似 on-policy**：数据只能短暂复用，随后必须丢弃并重新采样。

对比一下：

| 类型 | 数据来自谁 | 能否长期复用旧数据 | 例子 |
|---|---|---|---|
| on-policy / PPO | 当前或很接近当前的 policy | 只能少量复用 | 当前 LLM 生成的 rollout |
| off-policy | 可以来自旧 policy、日志或其他行为策略 | 通常可以配合校正长期复用 | DQN 的 replay buffer |

DPO 使用的是固定偏好数据集，不按“on-policy / off-policy 的 RL rollout”这条方式组织；不要把它硬套进 PPO 的概念。

## 2. batch 和 mini-batch 的区别

这里的 `batch` 有时会被不同框架叫成不同名字，容易混。我们用更明确的名称：

~~~text
rollout batch：一次新采集、并暂时固定的一整批 prompt + response
mini-batch：从 rollout batch 切出的一小块，供一次 forward → loss → backward → optimizer.step 使用
~~~

设：

~~~text
rollout_batch_size = 8     # 8 个 prompt，各采样 1 个回答
mini_batch_size = 2        # 每次只拿 2 个回答做一次参数更新
ppo_epochs = 4             # 整个 rollout batch 重复训练 4 遍
~~~

一轮 PPO 的实际节奏是：

~~~text
1. policy 一次采样 8 条 response             ← rollout batch
2. 将这 8 条随机拆成 4 个 mini-batch，每个 2 条
3. 第 1 个 epoch：依次训练 4 个 mini-batch      ← 4 次 optimizer.step()
4. 第 2 个 epoch：重新打乱，再训练 4 个 mini-batch
5. 第 3、4 个 epoch：同理
6. 共 4 × (8 / 2) = 16 次 optimizer.step()
7. 丢弃这 8 条 response，用更新后的 policy 新采 8 条
~~~

所以：

- `rollout batch` 决定一次收集多少“新鲜经验”，大一些通常让 reward/KL/advantage 的统计更稳定，但生成和显存成本更高；
- `mini-batch` 决定一次反向传播实际塞多少样本，主要受显存限制；小一些可以省显存，但一个 epoch 的更新步数更多、梯度噪声也可能更大；
- `ppo_epochs` 决定一批 rollout 最多重复利用多少遍。它太大时，policy 会离采样时的 old policy 太远，clip fraction / KL 往往上升，on-policy 性质变差。

在分布式训练里还会出现 `global_batch_size` 和 `per_device_batch_size`：前者是所有 GPU 汇总的样本数，后者是单张卡的样本数；但它们仍然都属于“这次收集或训练合计多少样本”的 batch 概念。

一句话记忆：**on-policy 说的是“数据是谁生成、是否新鲜”；mini-batch 说的是“这批数据每次切多大块来反传”。**

- 实际 PPO 通常不会存整块 logits（太占显存），而是 `log_softmax + gather` 后，只存 response 中实际被采样到的 token 的 `old_logp`，形状 `[B, T]`。
- `new_policy` 更准确应叫 **current policy**：它是同一个可训练 policy 在 PPO mini-batch 更新过程中的当前参数 `theta_current`。它对**同一条 `full_ids`**重新前向，产出当前的 logits `[B,L,V]`，再取出这条 response 实际 token 的 `new_logp [B,T]`。

可以写成：

~~~text
full_ids 不变： [prompt | y1 | y2 | ...]

采样时：theta_old  → logits_old [B,L,V]
                  → gather(response token)
                  → old_logp [B,T]   # 存档且 detach

更新期间：theta_current → logits_current [B,L,V]
                       → gather(同一 response token)
                       → new_logp [B,T]  # 保留梯度
~~~

然后：

~~~python
ratio = torch.exp(new_logp - old_logp)
~~~

它逐 token 表示：同一个已采样 token，在当前 policy 下的概率，相对采样时 old policy 的概率变了多少。

用一个 token 的数值例子：

~~~text
采样时 old policy 对实际选中的 token “不”的概率：0.10
old_logp = log(0.10)

经过若干次 optimizer.step 后，current policy 对同一个 token “不”的概率：0.12
new_logp = log(0.12)

ratio = exp(log(0.12) - log(0.10)) = 1.2
~~~

这里并不是拿 old policy 生成的回答和 new policy **重新生成**的另一份回答比较；两者评分对象始终是同一条 `full_ids`。变的是 model parameters，所以对同一个 token 给出的概率分布变了。

时间顺序再精确一点：

~~~text
1. theta_old 采样 response，并保存 old_logp。
2. 刚进入第一个 mini-batch、尚未 step 时：
   theta_current = theta_old，因此 new_logp ≈ old_logp，ratio ≈ 1。
3. 用该 mini-batch 的 loss.backward() + optimizer.step() 更新参数。
4. 下一个 mini-batch 或下一 PPO epoch：
   theta_current 已变；对同一 full_ids 重算，得到不同的 new_logp。
5. 但 old_logp 永远不改，始终是本 rollout batch 的锚点。
~~~

因此你的原句可以改写为：

> `old_policy` 在更新前对同一 `full_ids` 产生 logits，并从中保存实际 response token 的 `old_logp`；current/new policy 在更新中或更新后对同一 `full_ids` 重新产生 logits，得到 `new_logp`。

| current policy | 每个 mini-batch 的 step 后都变化 | `new_logp`，用于反传更新 |

~~~text
response: C  EOS              # 只有 2 个有效 token
~~~

~~~text
input_ids（B=2，L=2+4=6）
row 1:  P1  P2  A   B    C    EOS

attention_mask（真实输入位置为 1，PAD 为 0）
row 1:   1   1   1    1    1    1
~~~

|---|---|---|
| `attention_mask` | Transformer 注意力时不把 PAD 当有效上下文 | 0 |

## 问 2：logits 是怎么来的？为什么要“右移对齐”？

答：真实 Transformer 先对每个位置产生 hidden state，再由 LM head 做线性层：

~~~python
h = transformer(input_ids, attention_mask=attention_mask)  # B × L × H
logits = lm_head(h)                                        # B × L × V
# logits[b, i, :] = 在看完 input_ids[b, :i+1] 后，
#                   对“下一个 token”的 V 个原始分数
~~~

`logits` 不是概率，必须做 `softmax` 才是概率；做 `log_softmax` 才是 log-prob。

例如样本 1 在位置 `P2` 后要预测第一个回答 token `A`。假设这一位置的 logits（按 `A/B/C/EOS/PAD` 排列）恰好是：

~~~text
[0, 1, 2, 0, -1]
~~~

那么：

~~~text
Z = exp(0)+exp(1)+exp(2)+exp(0)+exp(-1)
  = 1 + 2.718 + 7.389 + 1 + 0.368 = 12.475

P(A) = exp(0) / Z = 1 / 12.475 ≈ 0.0802
log P(A) ≈ -2.524
~~~

注意这个因果语言模型的对齐关系：

~~~text
logits 的位置 0 预测 input_ids 的位置 1
logits 的位置 1 预测 input_ids 的位置 2
...
~~~

所以“`P2` 后预测 `A`”要取 `logits` 的位置 1；不是位置 2。

统一写成 PyTorch 的右移对齐：

~~~python
shift_logits = logits[:, :-1, :]       # B × (L-1) × V，位置 i 预测 i+1
shift_targets = input_ids[:, 1:]       # B × (L-1)，真实的下一个 token id
all_token_logp = F.log_softmax(shift_logits, dim=-1).gather(
    dim=-1,
    index=shift_targets.unsqueeze(-1),
).squeeze(-1)                           # B × (L-1)
~~~

对样本 1，`all_token_logp` 依次是在给：`P2、A、B、C、EOS` 这五个目标 token 打分；但 PPO 只取 response 的四个目标 token `A/B/C/EOS`。由于 prompt 长度是 `prompt_len=2`，第一个回答 token `A` 的 prediction 来自位置 `prompt_len - 1 = 1`：

~~~python
response_logp = all_token_logp[:, prompt_len - 1 : prompt_len - 1 + response_len]
# B × T = 2 × 4
~~~

这就是 policy 的“label 对齐”。

若写成 SFT 常见的 `labels`，它也表达同一份对齐规则：

~~~text
labels row 1:  -100  -100  A    B    C    EOS
labels row 2:  -100  -100  C    EOS  -100 -100
~~~

Hugging Face 的 causal-LM cross entropy 会在内部将 logits/labels 右移一格，因此 `P2` 位置 logits 对应标签 `A`。`-100` 表示忽略 prompt 和 PAD。

但要分清：**SFT 用 labels 做 CE loss；PPO 不把 `A/B/C/EOS` 当标准答案做 CE。** PPO 用同样的 token 对齐取出 log-prob，再乘 advantage，形成 policy loss。

## 问 3：rollout 时究竟保存哪些数？

答：用 `old policy` 对固定的 `input_ids` 前向后，不需要保存巨大的 logits；只保存实际 response token 的 log-prob 和 value。假设取出的结果为：

~~~text
old_logp（old policy 对实际采样 token 的 log-prob）
row 1 A/B/C/EOS:  -1.20  -0.80  -1.00  -0.50
row 2 C/EOS/PAD/PAD: -0.70  -0.40   0.00   0.00

old_values（policy 上 value head 的预估）
row 1:  1.00   1.20   1.50   2.00
row 2:  0.20   0.50   0.00   0.00
~~~

样本 2 后两个 `0.00` 只是占位；`response_mask=0`，它们不参与任何平均、GAE 或 loss。

同一条 `input_ids` 还要送进冻结的 `reference model`，但 reference **不生成新回答**。它只为已选定的 `A/B/C/EOS` 计算自己的 log-prob：

~~~text
ref_logp
row 1: -1.00  -0.90  -0.80  -0.60
row 2: -0.80  -0.30   0.00   0.00
~~~

RM 也读取“prompt + 完整 response”，每条输出一个标量：

~~~text
rm_reward row 1 = 3.00
rm_reward row 2 = 1.00
~~~

至此，response token 本身不再改变；接下来的计算只改变 policy/value 参数。

## 问 4：KL 奖励和 RM 分怎样变成每个 token 的 reward？

答：一种经典、便于理解的做法是先在每个 response token 上放一个采样 KL 近似：

~~~text
kl_sample = old_logp - ref_logp
token_reward = -kl_coef × kl_sample
~~~

设 `kl_coef=0.1`：

~~~text
样本 1 的 kl_sample:  -0.20,  0.10, -0.20,  0.10
KL token reward:       +0.02, -0.01, +0.02, -0.01

样本 2 的 kl_sample:  -0.10, -0.10
KL token reward:       +0.01, +0.01
~~~

然后把 RM 给整句的分数加到**每条样本最后一个有效 response token**：

~~~text
最终 token_rewards
row 1:  0.02  -0.01  0.02  2.99   # 最后是 -0.01 + RM 3.00
row 2:  0.01   1.01  0.00  0.00 # 最后是 +0.01 + RM 1.00
~~~

真实实现对 KL 的精确形式、奖励白化和是否额外加 KL loss 会有版本差异；这里使用“KL 作为 token reward”的常见讲法，便于把 GAE 手算清楚，**不要再额外把同一 KL 重复加一次 loss**。

## 问 5：GAE 在这个例子里具体算什么？

答：它用 `token_rewards` 和 `old_values`，从 response 末尾往前算出：

- `advantages`：这一步比当时 value 预期好多少，给 policy loss；
- `returns`：value head 应学会预测的目标，给 value loss。

取 `gamma=1`、`lambda=0.95`。对样本 1：

~~~text
old values: V1=1.00, V2=1.20, V3=1.50, V4=2.00；终止后的 V5=0
rewards:    r1=0.02, r2=-0.01, r3=0.02, r4=2.99

delta4 = r4 + V5 - V4 = 2.99 + 0 - 2.00 = 0.99
A4 = 0.99

delta3 = r3 + V4 - V3 = 0.02 + 2.00 - 1.50 = 0.52
A3 = delta3 + 0.95 × A4 = 0.52 + 0.9405 = 1.4605

delta2 = r2 + V3 - V2 = -0.01 + 1.50 - 1.20 = 0.29
A2 = 0.29 + 0.95 × 1.4605 = 1.6775

delta1 = r1 + V2 - V1 = 0.02 + 1.20 - 1.00 = 0.22
A1 = 0.22 + 0.95 × 1.6775 = 1.8136

returns = advantages + old_values
row 1 returns: 2.8136, 2.8775, 2.9605, 2.9900
~~~

样本 2 只算两个有效 token；PAD 不进循环：

~~~text
V1=0.20, V2=0.50, terminal V3=0
r1=0.01, r2=1.01

delta2 = 1.01 - 0.50 = 0.51
A2 = 0.51; return2 = 1.01

delta1 = 0.01 + 0.50 - 0.20 = 0.31
A1 = 0.31 + 0.95 × 0.51 = 0.7945; return1 = 0.9945
~~~

于是：

~~~text
advantages
row 1: 1.8136  1.6775  1.4605  0.9900
row 2: 0.7945  0.5100  0.0000  0.0000

returns
row 1: 2.8136  2.8775  2.9605  2.9900
row 2: 0.9945  1.0100  0.0000  0.0000
~~~

手算示例先不做 advantage normalization；真实训练通常会在所有 `response_mask=1` 的 token 上标准化 advantage。

## 问 6：第一次 PPO update 的 policy loss 怎么算？

答：第一次 update 前，`current policy` 参数还等于 `old policy` 参数。所以对同一 `input_ids` 重算，得到：

~~~text
new_logp = old_logp
ratio = exp(new_logp - old_logp) = 1
~~~

设 clip 范围 `epsilon=0.2`。每个有效 token 的 PPO objective 是：

~~~python
objective = min(
    ratio * advantage,
    clamp(ratio, 0.8, 1.2) * advantage,
)
~~~

此时 `ratio=1`，两项都等于 advantage。因此只在六个有效 token 上做 masked mean：

~~~text
sum advantages =
1.8136 + 1.6775 + 1.4605 + 0.9900 + 0.7945 + 0.5100
= 7.2461

policy_loss = - 7.2461 / 6 = -1.2077
~~~

为什么前面有负号？优化器做的是**最小化 loss**，而 PPO 想最大化 objective。所有 advantage 在本玩具例子中均为正，所以反向传播会提高这些已采样 token 的 log-prob。真实 batch 也会有负 advantage token；它们会被降低概率。

## 问 7：第一次 value loss 怎么算？

答：第一次 update 前 `new_values = old_values`。value head 要拟合刚得到的 `returns`：

~~~python
value_loss = 0.5 * masked_mean((new_values - returns.detach()) ** 2,
                               response_mask)
~~~

因为 `returns - old_values = advantages`，本例的 value loss 为：

~~~text
0.5 × mean(
  1.8136², 1.6775², 1.4605², 0.9900², 0.7945², 0.5100²
)
≈ 0.841
~~~

它会推动 value head：在每个回答位置，把预估回报从 `old_values` 往对应 `returns` 推近。`returns.detach()` 表示 returns 是固定监督目标，不允许梯度通过它回流去修改 reward/GAE 计算。

设 `vf_coef=0.5`，并且本例已将 KL 放入 token reward，则简化总 loss 是：

~~~text
total_loss = policy_loss + vf_coef × value_loss
           ≈ -1.2077 + 0.5 × 0.841
           ≈ -0.7872
~~~

框架执行：

~~~python
optimizer.zero_grad()
total_loss.backward()
optimizer.step()
~~~

这一步只更新 policy 的可训练参数（共享 backbone、LM head、value head）；RM、reference、`old_logp`、`old_values`、`returns` 都不更新。

## 问 8：第一次 step 后，clip 是怎样真正起作用的？

答：下一次用同一 batch 前向时，假设 sample 1 第 3 个 token `C` 的 `new_logp - old_logp = 0.25`。则：

~~~text
ratio = exp(0.25) ≈ 1.284
clip(ratio, 0.8, 1.2) = 1.2
A3 = 1.4605 > 0

unclipped objective = 1.284 × 1.4605 ≈ 1.875
clipped objective   = 1.2   × 1.4605 ≈ 1.753
min(...) = 1.753
~~~

这表示：尽管把 `C` 的概率继续抬高会让未裁剪目标更大，PPO 只认可最多约 20% 的相对提升，不再给越界方向额外收益。它不是绝对禁止参数越界，但会移除越界后的主要优化动力。

## 问 9：真实代码中 mask 应怎样写？

下面是本例的核心伪代码。重点看 `response_mask` 贯穿所有需要做平均的地方：

~~~python
# 生成后，right-pad 的 input_ids / attention_mask 已准备好。
# 注意：实际模型 token id，而非字符串。

logits, values_all = policy(input_ids, attention_mask=attention_mask)
shift_logits = logits[:, :-1, :]
shift_ids = input_ids[:, 1:]

all_logp = F.log_softmax(shift_logits, dim=-1).gather(
    -1, shift_ids.unsqueeze(-1)
).squeeze(-1)

# prompt_len 在本玩具 batch 中相同；真实变长 prompt 需为每个样本记录边界。
response_logp = all_logp[:, prompt_len - 1 : prompt_len - 1 + response_len]
values = values_all[:, prompt_len - 1 : prompt_len - 1 + response_len]

def masked_mean(x, mask):
    return (x * mask).sum() / mask.sum().clamp_min(1)

ratio = torch.exp(new_logp - old_logp)
policy_objective = torch.minimum(
    ratio * advantages,
    torch.clamp(ratio, 0.8, 1.2) * advantages,
)
policy_loss = -masked_mean(policy_objective, response_mask)
value_loss = 0.5 * masked_mean((new_values - returns.detach()).square(),
                               response_mask)
~~~

`attention_mask` 防止 PAD 进入 Transformer 上下文；`response_mask` 防止 prompt/PAD 进入 PPO 统计。二者都重要，不能互相替代。

## 问 10：这轮结束后发生什么？

答：同一 rollout batch 可以在有限的 `ppo_epochs` 内再切 mini-batch 重复几遍；每次都会重算 `new_logp/new_values`，但 `old_logp/old_values/returns/advantages` 保持该 batch 的快照。之后必须丢弃这批 response，用更新后的 policy 新采样下一批，以保持近似 on-policy。

## attention mask 和 causal mask 的区别

它们都作用在 self-attention 上，但解决的是完全不同的问题：

| mask | 解决的问题 | 哪些位置被屏蔽 |
|---|---|---|
| `attention_mask`（padding mask） | 这个 batch 为了对齐长度补出的 PAD 不是真实文本 | 所有 PAD 位置 |
| causal mask（因果/下三角 mask） | 预测当前位置时不能偷看未来 token | 当前 query 位置右侧的未来 token |

继续用前面的样本 2：

~~~text
位置:          0   1   2    3    4    5
input_ids:     P3  P4  C    EOS  PAD  PAD
attention_mask: 1   1   1    1    0    0
~~~

若只看 causal mask，它的规则是“位置 i 只能看位置小于等于 i 的 token”。以 `EOS` 所在位置 3 为例：

~~~text
causal mask 允许 EOS 位置关注：P3, P4, C, EOS
causal mask 禁止 EOS 位置关注：PAD, PAD（它们在未来）
~~~

但对另一个例子，若 PAD 出现在某个位置的**左侧**（常见于 left padding），因果规则会允许后续真实 token 看见它；这仍然不对，所以还必须有 `attention_mask` 把 PAD 屏蔽。

可以把两者理解成“取交集”：

~~~text
允许 attention(i, j)
= j 不是 PAD                  # attention_mask
  且 j <= i                    # causal mask
~~~

对 decoder-only LLM 来说，框架一般自动创建 causal mask；你通常传入的是 `attention_mask`，内部会把二者合并。注意一个实现细节：padding mask 最主要是屏蔽 **PAD 作为 key/value** 被其他 token 关注；PAD 位置自身仍可能产生无意义输出，但它会被 `response_mask=0` 和 labels 的 `-100` 排除，不进入 PPO/SFT loss。

第一步，算概率比：

~~~text

clip(ratio, 0.8, 1.2) = 0.8
~~~

负 advantage 的 PPO objective 仍用同一个公式：

~~~text
objective = min(ratio × A, clip(ratio) × A)

unclipped = 0.7 × (-2) = -1.4
clipped   = 0.8 × (-2) = -1.6
objective = min(-1.4, -1.6) = -1.6
~~~

训练最小化的是 `policy_loss = -objective`，所以这里：

~~~text
policy_loss = 1.6
~~~

为什么要取 `min`，而不是让概率继续从 0.07 降到 0.01？因为对负 advantage，降低这个坏 token 的概率是对的，但**降得过猛**仍会让 current policy 离 old policy 太远。

若没有 clipping：

~~~text
ratio 继续变小：0.7 → 0.5 → 0.1
ratio × A：     -1.4 → -1.0 → -0.2
~~~

PPO 是最大化 objective；`-0.2` 比 `-1.4` 大，所以优化器会不断得到“继续把坏 token 概率压到极低”的奖励，更新可能失控。

加入 clip 后，只要 `ratio < 0.8` 且 `A < 0`，`min` 会选常数的 `0.8 × A = -1.6` 这一支。该分支对 ratio 没有梯度，因此不会再鼓励把概率从 0.07 压得更低。

正负两种情况对称记忆即可：

| advantage | PPO 原本希望 | 超出 clip 区间后阻止什么 |
|---|---|---|
| `A > 0` | 提高已采样好 token 的概率 | 不要高于 `1 + epsilon` 太多 |
| `A < 0` | 降低已采样坏 token 的概率 | 不要低于 `1 - epsilon` 太多 |

因此，你上一条的两个 mask 可以压成一句：

~~~text
causal mask：不许偷看未来。
attention mask：不许把 PAD 当文本。
response mask：不许让 prompt/PAD 参与 PPO loss。
~~~

你算得完全正确：`A=-2, ratio=0.9` 时，`objective=0.9×(-2)=-1.8`，`policy_loss=-objective=+1.8`。而且 `0.9` 在 `[0.8, 1.2]` 内，所以此处**没有发生 clip，也没有停止梯度**。

先把总规则固定住：

~~~text
PPO 想最大化 objective
PyTorch 优化器习惯最小化 loss
所以 policy_loss = - objective
~~~

这个负号只是把“最大化”翻译成优化器能做的“最小化”，不是说负 advantage 就一定得到正 loss、正 advantage 就一定得到负 loss；**loss 的正负本身不是好坏判断**，关键是反向传播会让它怎样变小。

## 1. A 的正负：它告诉模型，这次采样的 token 应该变得更常见还是更少见

`A`（advantage）表示：该 token 所在这条后续轨迹，实际回报相对 value 的预期是好还是差。

| advantage | 含义 | 希望当前 policy 怎么改该已采样 token 的概率 | ratio 的目标方向 |
|---|---|---|---|
| `A > 0` | 比预期好 | 提高概率 | 变大 |
| `A < 0` | 比预期差 | 降低概率 | 变小 |

`ratio = p_current / p_old = exp(new_logp - old_logp)`。因此：

~~~text
ratio > 1：当前 policy 比采样时更偏爱该 token
ratio < 1：当前 policy 比采样时更不偏爱该 token
~~~

你的例子 `A=-2`：在没有触及 clip 时，

~~~text
objective = ratio × A = -2r
loss      = -objective = 2r
~~~

优化器要让 `loss=2r` 变小，因此会把 `r` 往小推，也就是降低这个坏 token 的 `new_logp` / 概率。

~~~text
r=1.0 → loss=2.0
r=0.9 → loss=1.8   # 更小，方向正确
r=0.8 → loss=1.6   # 还能继续降到边界
~~~

这里 `loss=+1.8` 不是“模型受罚所以要把概率调高”；恰好相反，梯度下降会让 `1.8` 继续往小走，于是 token 概率继续下降。

对照正 advantage。若 `A=+2`：

~~~text
objective = 2r
loss      = -2r
~~~

要最小化 `-2r`，就要让 `r` 变大，亦即提高这个好 token 的概率：

~~~text
r=1.0 → loss=-2.0
r=1.1 → loss=-2.2   # 更小，方向正确
r=1.2 → loss=-2.4
~~~

所以可记成一句：**A 的符号决定“推高还是压低概率”；loss 前的负号只负责把“想最大化的 PPO objective”改成“可最小化的 loss”。**

## 2. clip 究竟限制什么

设 `epsilon=0.2`，允许区间是 `[0.8, 1.2]`：

~~~python
unclipped = ratio * A
clipped   = clamp(ratio, 0.8, 1.2) * A
objective = min(unclipped, clipped)
loss = -objective
~~~

它不是简单地说“ratio 一出区间就完全不训练”，而是只在**已经朝正确方向推得太远**时，取消该 token 继续越界的额外收益。

| A | 正确的概率变化 | 越界区 | `min` 最终选中 | 对“继续越界”的梯度 |
|---|---|---|---|---|
| `A>0` | `r` 增大 | `r>1.2` | `1.2×A` | 0：不再鼓励继续增大 |
| `A<0` | `r` 减小 | `r<0.8` | `0.8×A` | 0：不再鼓励继续减小 |
| `A>0` | `r` 增大 | `r≤1.2` | `r×A` | 非 0，正常更新 |
| `A<0` | `r` 减小 | `r≥0.8` | `r×A` | 非 0，正常更新 |

注意负 advantage 时，`min` 的方向看起来会有点反直觉，因为乘上负数会反转大小关系。我们把你的例子完整列出来：

~~~text
A=-2，epsilon=0.2

r=1.0：unclipped=-2.0，clipped=-2.0，objective=-2.0，loss=2.0
r=0.9：unclipped=-1.8，clipped=-1.8，objective=-1.8，loss=1.8
r=0.8：unclipped=-1.6，clipped=-1.6，objective=-1.6，loss=1.6
r=0.7：unclipped=-1.4，clipped=-1.6，objective=min(-1.4,-1.6)=-1.6，loss=1.6
r=0.6：unclipped=-1.2，clipped=-1.6，objective=min(-1.2,-1.6)=-1.6，loss=1.6
~~~

`r` 从 `1.0` 降到 `0.8`，是在合理幅度内降低坏 token 概率，loss 从 `2.0` 降到 `1.6`。但 `r<0.8` 后，PPO 让 loss 固定为 `1.6`：从 `0.7` 再压到 `0.6`，这个 token 的 policy loss 一点也不会更好。

正 advantage 完全对称：

~~~text
A=+2
r=1.0 → objective=2.0, loss=-2.0
r=1.1 → objective=2.2, loss=-2.2
r=1.2 → objective=2.4, loss=-2.4
r=1.3 → unclipped=2.6, clipped=2.4
         objective=min(2.6, 2.4)=2.4，loss=-2.4
r=1.4 → 仍为 objective=2.4，loss=-2.4
~~~

也就是：好 token 可以被提高概率，但最多先认可到相对 old policy 的 `1.2` 倍；坏 token 可以被降低概率，但最多先认可到 `0.8` 倍。

## 3. “停止梯度”到底是什么意思

它**不是**：模型停训、整个 batch 不更新，或这个数被删掉。它的精确定义是：

~~~text
对这个 response token 的这个 PPO policy-loss 项，
loss 不再随 new_logp / ratio 的继续越界而变化。
因此该项的导数（梯度）为 0。
~~~

在刚才 `A=-2, r=0.7` 的例子里，`objective` 选中的是：

~~~text
0.8 × (-2) = -1.6
~~~

其中 `0.8` 是 clamp 后的常数。无论 `r=0.7、0.6` 还是 `0.1`，这一个分支都还是 `-1.6`，所以反向传播无法从这个 loss 项得到“再把 r 压低一点会更好”的信号。

但仍有三个边界要记住：

- 同一个 mini-batch 的其他 token 仍可能有梯度；
- value loss、entropy bonus 等其他 loss 项仍可能有梯度；
- 参数由所有 token 共享，即使这个 token 的 PPO 项梯度为 0，其他项更新参数后，它的概率也可能被连带改变。

因此更严谨的说法是：**clip 停止的是“这个 token 因继续往危险方向越界而获得的 policy-gradient 激励”，不是冻结整个模型，也不是保证 ratio 永远不会越界。**

最后给你一个一眼判断法：

~~~text
A>0：先看 ratio 是否高于 1+epsilon；高于才被截断。
A<0：先看 ratio 是否低于 1-epsilon；低于才被截断。
~~~

所以你的 `A=-2, r=0.9`：应继续降低概率、尚未触边、没有 clip、梯度非零。

小检查：若 `A=+3、r=1.3、epsilon=0.2`，请算 `unclipped objective`、`clipped objective` 和 `loss`；并判断这个 token 还会不会因为“继续提高概率”得到 policy-loss 的梯度。

~~~python
shift_logits = logits[:, :-1, :]          # [B, L-1, V]
shift_targets = input_ids[:, 1:]          # [B, L-1]

all_logp = F.log_softmax(shift_logits, dim=-1).gather(
    dim=-1,

response_logp = all_logp[:, Q-1 : Q-1+T]  # [B, T]

)
policy_loss = -masked_mean(objective, response_mask)
~~~

~~~text
SFT：gather/labels 后，强迫模型模仿标准答案（cross entropy）。
PPO：gather 已采样 response 后，用 advantage 决定提高或降低其概率。
~~~

好，跳过 ratio。下一题看 PPO 的 **value head 与 GAE**：它解决“RM 通常只给整句一个分数，为什么 PPO 能对 response 的每个 token 算 advantage”。

## 问 1：value head 到底预测什么？

response 有 4 个 token：

~~~text
response: A   B   C   EOS
位置:       1   2   3   4
~~~

在生成到每个位置时，value head 都看当前已有上下文，输出一个标量 `V_t`：

~~~text
V_t = 从当前位置开始，按当前 policy 继续生成，预期还能得到多少未来回报
~~~

它通常挂在 policy 的同一个 Transformer backbone 上：

~~~text
hidden_states: [B, L, H]     # policy backbone 的每位置表征
value_head:    Linear(H, 1)
values:        [B, L]        # 每个位置一个 value 标量
~~~

它不是在预测下一个 token，也不输出 `[B,L,V]` 词表分布；它输出的是“未来回报的估计”。

## 问 2：整句 RM reward 怎样变成 token reward？

真实 RLHF 中 RM 往往为整句 `prompt + A B C EOS` 给一个标量，例如 `RM=3.0`。一种常见、便于理解的归因方式是：把它加在最后一个有效 token 上；再在每步放 KL 代价。

假设 KL 项已经算完，最终 token reward 是：

~~~text
r1 =  0.02        # A 位置的小 KL 修正
r2 = -0.01        # B 位置的小 KL 修正
r3 =  0.02        # C 位置的小 KL 修正
r4 =  2.99        # EOS 位置：RM 3.0 + KL 修正 -0.01
~~~

所以 RM 没有神奇地直接判断“哪个字好、哪个字坏”。它只说：**完整回答最终得了较高分**。credit assignment（哪些早期选择应负责）主要由 value/GAE 来估计。

## 问 3：先不加 GAE，只从结尾倒推会怎样？

为了先看清核心，取 `gamma=1`。完整回答的总回报是：

~~~text
G4 = r4                 = 2.99
G3 = r3 + G4            = 3.01
G2 = r2 + G3            = 3.00
G1 = r1 + G2            = 3.02
~~~

早期的 `A/B/C` 虽然没有直接拿到 RM 的 3 分，但它们是导致最终回答出现的前置决策，所以它们也应该感受到“未来得到的这笔回报”。这就是为什么不能只更新 EOS。

但如果直接拿 `G_t` 更新，方差通常很大：不同 prompt 的回报天生尺度不同，PPO 很难判断“3 分到底算好还是普通”。于是减去 value 这个基线。

## 问 4：advantage 为什么是“实际回报 − 预期回报”？

假设 rollout 时 value head 的预估为：

~~~text
old_values
V1=1.00, V2=1.20, V3=1.50, V4=2.00
~~~

直观地说：

~~~text
实际未来回报 > V_t：超出预期，A_t 应为正，增强这一步 token 的概率
实际未来回报 < V_t：不如预期，A_t 应为负，降低这一步 token 的概率
~~~

最朴素的蒙特卡洛版本会写：

~~~text
A_t = G_t - V_t
~~~

例如第 4 位：`A4 = 2.99 - 2.00 = +0.99`。表示生成到 EOS 前，模型预期还值 2 分；实际拿到了 2.99 分，比预期好 0.99。

## 问 5：GAE 多做了什么？

GAE 不直接把很远的最终分数原样搬回前面，而是先计算每一步的 **TD residual（一步预测误差）**：

~~~text
delta_t = r_t + gamma × V_{t+1} - V_t
~~~

终止后没有未来，所以 `V5=0`。取 `gamma=1`、`lambda=0.95`：

~~~text
delta4 = 2.99 + 0    - 2.00 = 0.99
delta3 = 0.02 + 2.00 - 1.50 = 0.52
delta2 = -0.01 + 1.50 - 1.20 = 0.29
delta1 = 0.02 + 1.20 - 1.00 = 0.22
~~~

再从尾到头累加这些误差，越远的误差乘更小的 `lambda`：

~~~text
A4 = delta4 = 0.99
A3 = delta3 + 0.95×A4
   = 0.52 + 0.95×0.99 = 1.4605
A2 = delta2 + 0.95×A3
   = 0.29 + 0.95×1.4605 = 1.6775
A1 = delta1 + 0.95×A2
   = 0.22 + 0.95×1.6775 = 1.8136
~~~

这四个 `A1..A4` 才会交给我们已经学过的 PPO clip loss。这里全为正，因此这一条回答的各 response token 都得到“相对预期做得不错”的增强信号。

`lambda` 是 bias/variance 旋钮：

| `lambda` | GAE 更像什么 | 特点 |
|---|---|---|
| `0` | 只看一步 `delta_t` | 方差低，但依赖 value 预测准确 |
| `1` | 接近完整的未来回报 | 信号完整，但方差更高 |
| `0.95` | 两者折中 | PPO 常见起点，具体仍需实验验证 |

## 问 6：value head 自己怎么学习？

GAE 算完后，给每个位置构造一个 value 的监督目标：

~~~text
returns_t = old_values_t + advantages_t
~~~


顺便校正两个小术语：

- 实际 Transformer 输出一般是 `[B, L, H]`，`L = prompt + response`；PPO 只在切片后对 response 部分得到 `[B,T,...]`。
- `lm_head` 在多数 decoder-only LLM 中通常是一个线性投影 `Linear(H,V)`（有时与输入 embedding 权重绑定），不一定是 MLP。value head 才常见为 `Linear(H,1)`，也可能是小 MLP。

## LoRA 参数上到底发生了什么？

设注意力层的 query 投影冻结的原权重是 `Wq`，LoRA 增量为：

~~~text
Wq_effective = Wq_frozen + scale × Bq × Aq
~~~

对 value 投影 `Wv` 也一样。若 `Aq/Bq/Av/Bv` 是 policy 中唯一可训练的 backbone 参数，则总 loss：

~~~python
total_loss = policy_loss + vf_coef * value_loss
total_loss.backward()
~~~

反传到同一个 LoRA 参数 `phi` 时，Autograd 做的是梯度相加：

~~~text
grad_phi = grad_phi(policy_loss)
         + vf_coef × grad_phi(value_loss)
         + 其他可选项（entropy / KL 等）
~~~

然后 optimizer 只对这一个 `phi` 做一次 step。

所以：

- LM head 参数只收到 `policy_loss` 的梯度（及任何直接依赖 logits 的附加项）；
- value head 参数只收到 `value_loss` 的梯度；
- **共享 Q/V LoRA 参数同时收到 policy loss 和 value loss 的梯度。**

## 什么叫“冲突”？

如果两股梯度在 LoRA 参数空间方向相近，会互相帮助：同一套表征既更能支持“预测哪个 token 值得提高概率”，也更能支持“预估未来回报”。

如果方向相反，例如 policy 希望 Q/V 表征更强化某种生成偏好，但 critic 为降低自己的预测误差想朝相反方向改，那么两者会部分抵消。这就是梯度冲突。共享 backbone 的多任务训练里很常见，PPO 并不保证它绝不会发生。

但多数实现仍选择共享，主要是因为：

1. **省显存和算力**：不需要为 critic 再复制一个大 Transformer；
2. **共享有用表征**：预测“这个前缀未来可能获得的回报”和决定“下一 token 的分布”都需要理解 prompt/response 的语义；
3. **可用权重控制权衡**：`vf_coef` 把 value 梯度的影响缩放到合适程度。

若你发现 critic 更新压制了 policy 学习，或 value loss 极大/训练不稳定，常见处理不是直接认定“LoRA 不能用于 PPO”，而是依次检查：

- 调低 `vf_coef`，让 value loss 对共享 LoRA/backbone 的影响变小；
- 调整 value clipping、学习率、critic 更新轮数与 advantage normalization；
- 让 value head 自己保持可训练，但冻结部分或全部 shared LoRA/backbone（critic 只能学小头，容量会受限）；
- 用独立 critic / 单独的 LoRA adapter，让 policy 与 value 不再共享 adapter，代价是显存、算力和工程复杂度上升；
- 在研究型多任务场景，才会考虑 gradient surgery（例如 PCGrad）这类专门的冲突缓解方法；它不是标准 PPO 的必配项。

因此可以把 LoRA-PPO 的参数更新分成三类记：

| 参数 | policy loss | value loss |
|---|---:|---:|
| LM head | 是 | 否 |
| value head | 否 | 是 |
| shared Q/V LoRA | 是 | 是（乘 `vf_coef`） |

```text
advantage 的数值：作为这次 rollout 对 token 好/坏的固定判据
advantage 的梯度：是否允许 optimizer 反过来修改这个判据
```

PPO 要的是前者，不要后者。`detach()` **不改变 advantage 的数值，只切断“从 policy loss 回到旧 value”的反向梯度路径**。

先用一个只有一个 token、回答已结束的极简例子。设环境/RM 给出的真实奖励固定为：

```text
R = +1
old_value = V = 0
advantage = R - V = 1
ratio = r
policy_loss = - r × advantage
```

正确做法中，rollout 阶段已经得到并存档：

```python
advantages = (reward - old_value).detach()  # 数值是 1，固定住
policy_loss = -ratio * advantages
```

此时为了降低 `policy_loss`，模型只能通过当前的 `ratio` 变大，即提高已采样 token 的 `new_logp` / 概率。这正是我们想要的 actor 更新。`old_value` 只是这次训练的固定基线，不能再动。

反过来，假如错误地不 detach，并且让 policy loss 仍连接到：

```text
advantage = R - V
policy_loss = -r × (R - V)
```

把 `R=1, V=0, r=1` 代入，当前 loss 为 `-1`。这时 optimizer 有两条让 loss 继续变小的路：

```text
路 1（正确的学习）：提高 r
  r: 1 → 1.1
  loss: -1 → -1.1
  含义：提高这个 token 的概率

路 2（作弊的捷径）：降低 V
  V: 0 → -0.5
  advantage: 1 - (-0.5) = 1.5
  loss: -1 × 1.5 = -1.5
  含义：token 的概率根本没变，
        只是 critic 把“原本预期回报”报得更低，
        从而把同一份奖励伪造成了更大的 advantage。
```

这就是“通过改 value 预测来改 advantage”的具体含义。reward `R` 是外部给定的事实；baseline `V` 只是预测。actor 不应该靠随意压低 baseline，让所有已采样 token 看起来都比预期好，来降低 policy loss。

甚至当奖励较差时它也会乱：若 `R=-1`、`V=0`，原本 `A=-1`，actor 应降低该 token 概率；但若允许 policy loss 改 `V`，它可以把 `V` 压到 `-2`，于是 `A=(-1)-(-2)=+1`，把一个坏样本伪造成“好样本”。

因此一轮 PPO 的时间顺序必须是：

```text
1. rollout（no_grad）：old policy/value 采样，得到 old_logp、old_values、reward
2. 用这些旧张量计算 advantages、returns，并 detach 成固定训练标签
3. 当前模型前向：得到 new_logp、new_values
4. policy_loss 仅用 new_logp + 固定 old_logp/advantages
5. value_loss 让 new_values 拟合固定 returns
```

```python
# 1-2：采样后，都是固定常数
advantages, returns = compute_gae(rewards, old_values)
advantages = advantages.detach()
returns = returns.detach()

# 3-5：只有 current 前向输出保留梯度
out = policy_with_value_head(full_ids)
policy_loss = ppo_loss(out.new_logp, old_logp, advantages)
value_loss = mse(out.new_values, returns)
```

注意：value head 并没有因此不训练；它仍从 `value_loss` 获得梯度，去拟合 `returns`。只是这次 actor 的 `policy_loss` 不能反过来篡改自己的评分基线。

时间线是：

```text
A. 本轮 rollout：参数记为 θ_old
   full_ids → old_values（保存、detach）
   full_ids → reward
   old_values + rewards → advantages、returns（固定）

B. 本轮 PPO 更新：参数变为 θ_current
   同一 full_ids → new_values（每个 optimizer.step 后会变化）
   value_loss = MSE(new_values, 固定的 returns)
```

对应代码：

```python
# A. rollout；通常 no_grad
old_values = old_policy(full_ids).values_on_response  # [B,T]
advantages = compute_gae(rewards, old_values)
returns = (old_values + advantages).detach()          # [B,T]，固定 target

# B. PPO mini-batch；有梯度，重复若干 epoch
new_values = current_policy(full_ids).values_on_response
value_loss = 0.5 * masked_mean((new_values - returns).square(), response_mask)
```

为什么不能写成 `returns = new_values + advantages`？因为 `new_values` 正是我们想训练的预测量。若它也在 target 里移动，就成了“学生一边答题，一边改标准答案”。例如：

```text
固定 target 的正确形式：
returns = 3
new_value: 1 → 2
MSE: (1-3)²=4 → (2-3)²=1   # 只能让预测接近 3

错误的移动 target：
returns = new_value + A，A=2
new_value=1 时：loss=(1-(1+2))²=4
若对 returns 不 detach，它会和 new_value 一起随参数移动，
会引入不该有的梯度路径；target 不再是 rollout 时固定的回报估计。
```

再补一个例外帮助你建立直觉：当 `gamma=1, lambda=1` 且回答终止时，`returns` 会退化为从当前位置开始的实际 sampled reward-to-go；代数上旧 value 会相消。

```text
returns_t = old_value_t + advantage_t
          = 实际后续 reward 的累加
```

但标准 PPO 常用 `lambda < 1` 的 GAE（例如 0.95）来降低方差，`advantages/returns` 中会包含后续 `old_values` 的 bootstrap 信息。因此通用实现仍必须用 rollout 时的 `old_values` 来构造并冻结 target。

一句话记：**old values 用来“出题”（构造固定 returns）；new values 用来“答题”（拟合 returns）。**

你会乱是正常的：PPO 里的 `batch/epoch` 和普通 SFT 不是同一层次。我们先暂停细节，只固定一个可运行的配置：

```text
rollout_batch_size = 8    # 一次新拿 8 个 prompt，并各生成一个 response
mini_batch_size   = 2    # 每次反传只处理其中 2 条 response
ppo_epochs        = 3    # 同一批 8 条 response 最多复用 3 遍
```

这一轮会有：

```text
一个 rollout batch = 8 条新经验
每个 epoch = 8 条打乱后切成 4 个 mini-batch
3 个 epoch = 3 × 4 = 12 次 optimizer.step()
```

注意：这里的一个 `epoch` 不是“把整个训练数据集跑一遍”，而是“把**当前这批固定的 8 条 rollout**完整训练一遍”。PPO 训练会不断重复“新采 8 条 → 训练 3 遍 → 丢弃 → 再新采 8 条”。

## 先记三层，不要混

```text
PPO iteration（一次完整循环）
└── rollout batch：8 条新生成的 prompt + response
    └── PPO epoch：把这 8 条完整用一遍
        └── mini-batch：每次取 2 条，forward/backward/step 一次
```

下面按真实时间顺序走一遍。

## 0. 取 prompt：尚未训练

从 prompt 池随机抽 8 个 prompt，例如 `p0 ... p7`。此时参数记为 `θ_old`。

```text
当前 policy(θ_old)
  + 8 个 prompts
  ↓
准备采样
```

这 8 个 prompt 加各自生成的 response，合起来才叫本轮的 **rollout batch**。

## 1. rollout / 采样：生成新数据并存档

用当前 policy `θ_old`，为每个 prompt 自回归采一条 response。比如共得到：

```text
p0 → r0 = “A B EOS”
p1 → r1 = “C EOS”
...
p7 → r7 = “D E F EOS”
```

把 prompt 和 response 拼成 `full_ids = [prompt | response]`，padding 后形成张量；同时得到 `attention_mask` 与 `response_mask`。这一阶段通常在 `torch.no_grad()` 下做，因为它是在收集经验，不是反传训练。

本轮**必须保存**下面这些固定数据：

| 保存什么 | 从哪里来 | 后面为什么要用 |
|---|---|---|
| `full_ids`、`attention_mask`、`response_mask` | prompt + 已采样 response | 后续用同一条回答重算当前 logp/value；mask 掉 prompt/PAD |
| `old_logp [8,T]` | `θ_old` 对实际采样 response token 的 log-prob | PPO ratio 的锚点：`exp(new_logp-old_logp)` |
| `old_values [8,T]` | rollout 时 value head 的输出 | 和 reward 一起构造 GAE / `returns` |
| `reward`（及可选 `ref_logp`） | RM 打分；参考策略用于 KL | 给这条回答最终反馈，并构造每 token reward |

一个很重要的词：`old` 不是“上一次 PPO iteration 的模型”。它是**本轮 8 条 response 采样时**的那份 policy/value 输出快照。可以不保留一整份 `old` 模型副本，但必须保存 `old_logp/old_values` 这些数字。

到这一步为止，模型参数还没有更新。

## 2. 整理训练标签：一次算好，随后冻结

对这 8 条 response，用 reward、`old_values`（以及可选 KL reward）计算：

```text
advantages [8,T] = compute_gae(rewards, old_values)
returns    [8,T] = old_values + advantages
```

随后：

```python
old_logp   = old_logp.detach()
old_values = old_values.detach()
advantages = advantages.detach()
returns    = returns.detach()
```

这些现在都是本轮 rollout 的**固定档案/标签**：3 个 epoch、12 个 step 中一律不变。

为什么？

- `old_logp` 不变，ratio 才能表示“当前 policy 相对采样时 policy 偏了多少”；
- `advantages` 不变，actor 才是在同一个好/坏判据下调整 token 概率；
- `returns` 不变，critic 才是在拟合固定回报目标，而不是一边预测一边改答案。

至此，8 条数据都已收集完成；才进入训练。

## 3. PPO epoch 1：把同一批 8 条切成 mini-batch

先随机打乱索引：

```text
本 epoch 的顺序：[p3, p0, p7, p2, p1, p5, p4, p6]

mini-batch 1: [p3, p0]
mini-batch 2: [p7, p2]
mini-batch 3: [p1, p5]
mini-batch 4: [p4, p6]
```

每一个 mini-batch 都执行同一套动作。以第一个 `[p3, p0]` 为例：

```text
固定读入：
  full_ids / masks
  old_logp / old_values / advantages / returns

当前模型 θ_current 前向（带梯度）：
  full_ids → logits → new_logp
  full_ids → value head → new_values

算 loss：
  policy_loss = PPOClip(new_logp, old_logp, advantages)
  value_loss  = MSE(new_values, returns)
  total_loss  = policy_loss + vf_coef × value_loss (+ 可选 entropy/KL)

反传更新：
  optimizer.zero_grad()
  total_loss.backward()
  optimizer.step()
```

这里发生了**第 1 次参数更新**：LM head、value head、以及共享 backbone/LoRA 中各自能收到梯度的参数都会改变。

接着跑 mini-batch 2；因为刚刚已经 `step()`，此时 `θ_current` 已经不同，所以同样固定的 `full_ids` 重新前向得到的 `new_logp/new_values` 会和上一 mini-batch 时不同。

但下面这些绝不变：

```text
response token 本身、full_ids、old_logp、old_values、advantages、returns
```

Epoch 1 完成后，刚好训练过 8 条一次，共 4 次 step。

## 4. PPO epoch 2、3：复用同一批数据，但模型已变

每个新 epoch 都重新打乱 8 条的顺序，再切成 4 个 mini-batch。仍然使用**同一批 response 和同一组固定档案**，但 policy 参数已因前面的 step 改变，所以每次新前向的：

```text
new_logp、new_values、ratio、policy_loss、value_loss
```

都会变化。3 个 epoch 共得到 12 次 step。

为什么允许复用 3 遍？一次 rollout 很贵；只更新一次会浪费这些已付出生成/RM 打分成本的数据。为什么又不能无限复用？因为 response 来自 `θ_old`，参数经过太多 step 后会离 `θ_old` 太远，数据不再近似 on-policy；PPO 的 ratio/clip 能缓冲短暂复用，但不是无限次回放的许可证。

## 5. 丢弃 rollout batch，开始下一轮

经过 12 次 step 后，当前参数已成为新的 `θ_new`。此时不再拿旧的 8 条 response 继续训练，而是：

```text
θ_new
  + 新抽的 8 个 prompts
  ↓
生成新的 8 条 response
  ↓
保存新的 old_logp / old_values / rewards
  ↓
再训练 3 epochs
```

“丢弃”指不再把旧 rollout 当 PPO 训练数据；训练日志、checkpoint 通常仍会保存。

## 最后用一张表定住“谁会变”

| 对象 | 在何时产生 | 同一 rollout 的 3 epochs 内会变吗 | 原因 |
|---|---|---:|---|
| `full_ids` / response | rollout 采样 | 否 | 同一批经验不能换回答 |
| `old_logp` | rollout | 否 | PPO ratio 的基线 |
| `old_values` | rollout | 否 | GAE/returns 的旧 critic 快照 |
| rewards | rollout 后 RM/KL 计算 | 否 | 对已采样回答的固定反馈 |
| advantages / returns | rollout 后计算 | 否 | actor/critic 的固定训练标签 |
| `new_logp` | 每个 mini-batch 前向 | 是 | policy 每个 step 都在更新 |
| `new_values` | 每个 mini-batch 前向 | 是 | value head/backbone 每个 step 都在更新 |
| policy/value/LoRA 参数 | 每次 `optimizer.step()` | 是 | 训练目标就是更新它们 |

把全流程压成一句就够了：

```text
先用旧快照生成并冻结一批“经验和答案”；
再把它切成小块，有限次数地训练当前模型去提高好 token 概率、降低坏 token 概率，并拟合固定回报；
然后重新采样新经验。
```

现在进入“看训练仪表盘”这一层。核心结论：**不要只看 `total_loss` 或 reward；PPO 要同时看 policy 是否偏离太快、clip 是否大量触发、critic 是否在学、以及实际 reward/任务评测是否改善。**

仍沿用一轮 rollout：`old_logp` 固定，训练过程中反复得到 `new_logp`。对每一个有效 response token：

```text
log_ratio = new_logp - old_logp
ratio     = exp(log_ratio)
```

## 1. ratio：看“相对采样时 policy 变了多少”

```text
ratio = 1：该 token 的当前概率与采样时相同
ratio > 1：当前 policy 更偏爱该已采样 token
ratio < 1：当前 policy 更不偏爱该已采样 token
```

单个 ratio 不能单独判断好坏，因为它必须和 advantage 一起看：

```text
A > 0，ratio 上升：正确方向（提高好 token 概率）
A < 0，ratio 下降：正确方向（降低坏 token 概率）

A > 0，ratio 下降：反方向
A < 0，ratio 上升：反方向
```

因此实际日志通常看一批有效 token 上的分布/均值，而不是盯一个 token。若大量 ratio 很快远离 1，说明当前 policy 已经离本轮采样 policy 较远。

## 2. clip fraction：看“有多少 token 已撞上 PPO 护栏”

设 `epsilon=0.2`：

```python
clip_fraction = masked_mean(
    (torch.abs(ratio - 1.0) > 0.2).float(),
    response_mask,
)
```

例如有效 token 有 100 个，其中 18 个 `ratio < 0.8` 或 `ratio > 1.2`：

```text
clip_fraction = 18 / 100 = 0.18
```

它的含义是：18% 的 token 已经偏离 old policy 超过允许区间。

```text
clip fraction 接近 0，且 reward 没改善
  → 更新可能太小，或 advantage / reward 信号太弱

clip fraction 适中
  → 需要结合 reward、KL 一起判断；没有一个放之四海而皆准的“正确值”

clip fraction 很高且持续上升
  → 大量 token 已触发护栏，当前 batch 复用过度或更新过猛
  → 常见动作：减少 ppo_epochs、降低 learning rate、减小 mini-batch 的累积更新强度，或更早停止本轮 epoch
```

注意：它统计的是“越过区间”的比例；严格说，只有越界方向与 advantage 一致时，PPO objective 才会选中平坦的 clipped 分支、使该 token 的 policy 梯度停止。

## 3. KL：要先分清两种参照物

“KL 变大”本身不够完整，必须问：**current 在跟谁比？**

```text
A. approx_kl(old || current)
   比较本轮采样时的 old policy 与 current policy
   用途：监控本轮 PPO 更新步子是否太大

B. ref_kl(current || reference)
   比较 current policy 与冻结的 SFT reference policy
   用途：约束最终模型不要偏离原始 SFT 行为/语言能力太远
```

在 rollout 的已采样 token 上，常见的近似监控量是：

```python
log_ratio = new_logp - old_logp
approx_kl_old_current = masked_mean(
    (torch.exp(log_ratio) - 1) - log_ratio,
    response_mask,
)
```

它非负，接近 0 代表 current 与 old 很接近；训练后期若快速增大，说明一个 rollout batch 被更新得太远。许多实现会设 `target_kl`：超过阈值就提前结束该 rollout 的剩余 PPO epochs。

参考模型 KL 则常进入每 token reward，例如：

```text
reward_t = RM_terminal_reward - beta_kl × (new_or_old_logp - ref_logp)
```

具体符号/计算时机因实现不同，但目的相同：生成越偏离 reference，越要付 KL 代价。

## 4. value loss：看 critic 是否在逼近固定 returns

```python
value_loss = 0.5 * masked_mean((new_values - returns).square(), response_mask)
```

```text
稳定下降或逐步稳定：通常说明 critic 在学习本批回报结构
长期很大且无改善：critic 可能学不动；returns 尺度、vf_coef、学习率、value head 容量等需排查
突然剧烈爆涨 / NaN：训练数值不稳定，需要先止损检查
```

但 `value_loss` 低不等于模型回答一定更好：它只说明 critic 更像这批固定 `returns`，不等于 RM/真实任务 reward 变好。反过来，早期 value loss 很高也不一定要立刻停，因为 critic 初期确实会不准。

可以再配合 `explained_variance` 看 critic 是否比“只预测 returns 的均值”更有解释力：

```text
EV = 1 - Var(returns - new_values) / Var(returns)

接近 1：预测解释了大部分 returns 波动
接近 0：和只预测均值差不多
小于 0：比预测均值还差
```

当本 batch 的 returns 几乎没有方差时，这个指标会不稳定，不应孤立解读。

## 5. 把四个信号放在一起读

| 现象 | 更可能的解释 | 优先排查/动作 |
|---|---|---|
| reward/任务指标无改善；ratio 近 1、clip fraction 近 0、old-current KL 很低 | policy 更新力度不足，或 advantage 信号很弱 | 学习率、ppo_epochs、reward/advantage 尺度与归一化 |
| KL 与 clip fraction 快速升高；同一 rollout 后几个 epoch 尤其明显 | 更新太猛、复用旧 rollout 太久 | 降 learning rate / ppo_epochs；设 target-KL early stop |
| value loss 高或 EV 很差，但 KL/clip 正常 | critic 跟不上，actor 信号可能噪 | 检查 returns/reward 尺度、vf_coef、value LR/容量 |
| value loss 很低，reward/真实评测变差 | critic 只是拟合当前目标；RM 被 exploit 或 reward 与目标错位 | 回看 RM、KL、人工/离线任务评测与失败样本 |
| reward 上升但 ref-KL 失控 | 可能在为了 RM 分数过度偏离 SFT/reference | 调 KL 系数，检查 reward hacking 和定性样本 |

因此一个健康训练不能被简化成“loss 越低越好”。更接近的目标是：**有真实 reward/任务改善，同时 old-current KL 与 clip fraction 没有过快恶化，critic 也在逐渐跟上。**


因此它们常被统称为 **actor-critic 架构**：

- actor 负责“行动”——在 LLM 里每一步选择哪个 token；
- critic 负责“评价预期”——当前前缀之后大概能拿多少回报；
- RM 负责“事后打分”——这整条 response 实际得到多少 reward。

~~~text
分母 = 10
value_loss = 0.5 × 16 / 10 = 0.8
~~~

于是日志会报告 `value_loss=0.8`，看上去 critic 不准；实际上它对所有真实 response token 都是正确的。这个 0.8 完全是 PAD 伪造出来的。

再看反向传播。对被 mask 选中的某个位置，MSE 项对 value 输出的导数是：

~~~text
∂ value_loss / ∂ new_value_i = (new_value_i - return_i) / N
~~~

这里错误 mask 下 `N=10`：

- 前 6 个真实位置：`(v-target)/10=0`，没有梯度，因为本来已经预测正确。
- 每个被误纳入的 PAD：`(2-0)/10=+0.2`。梯度下降会把该位置的 value 从 2 往 0 推。

所以 value head 和共享 backbone/LoRA 收到的主要信号变成：**“请把 PAD 位置预测成 0”**，而不是“请更准确地预测真实 token 前缀之后的回报”。这就是学习容量与梯度被无效监督占用；若 PAD 比例高，critic 训练会明显被带偏。

还有一种更隐蔽的情况：假如模型在 PAD 上恰好已经输出 0，那么 PAD 平方误差为 0，不会制造额外误差；但它们依然错误地进入了分母，稀释真实 token 的 loss 和梯度。

例如仍是 6 个有效位置、4 个 PAD，假设真实 token 的平方误差总和为 6，而 4 个 PAD 的误差恰好都为 0：

~~~text
正确 mask：value_loss = 0.5 × 6 / 6  = 0.5
错误 mask：value_loss = 0.5 × 6 / 10 = 0.3
~~~

真实预测完全没变，错误实现却显示 loss 从 `0.5` “改善”成 `0.3`；同时每个真实位置的梯度也从除以 6 变成除以 10，只剩原来的 `6/10`。critic 看起来更好，实际上学得更慢。

因此要记两种扭曲：

- PAD 输出不等于占位 target：产生假 loss、假梯度，模型被推去拟合 PAD。
- PAD 输出刚好等于占位 target：loss 被分母稀释，真实 token 的学习信号被削弱，指标还会虚假好看。

补一个实现边界：不同代码库未必真的为 PAD 构造 `return=0`，有的 PAD 区间是任意填充值；但结论不变——**PAD 必须在 GAE、returns、value loss、统计指标中都由 `response_mask=0` 排除。**`attention_mask=0` 只是不让模型在 attention 中把 PAD 当作上下文，不能自动让 PPO/value loss 忽略它。

```text
attention_mask：模型前向时，哪些位置是真实序列、PAD 不应参与 attention
response_mask ：PPO 哪些 token 是需要训练/统计的有效 response

```

第三个在很多实现里并不是新建一张 mask，而是直接复用 `response_mask`；关键不是张量叫不叫什么名字，而是 **PAD 不能进入 GAE、returns、policy loss 或 value loss。**

下面用一个 batch，`B=2`、prompt 长度 `Q=3`、response 最大长度 `T=4`。第 0 条恰好生成 4 个 token；第 1 条只生成 2 个 token，后面补两个 PAD。于是完整长度 `L=Q+T=7`：

~~~text
full_ids[0] = [P1, P2, P3, A1, A2, A3, A4]
full_ids[1] = [P1, P2, P3, B1, B2, PAD, PAD]

attention_mask[0] = [1, 1, 1, 1, 1, 1, 1]
attention_mask[1] = [1, 1, 1, 1, 1, 0, 0]     # 整段真实长度不同

response_mask[0]  = [1, 1, 1, 1]              # 对应 A1..A4
response_mask[1]  = [1, 1, 0, 0]              # 对应 B1,B2,PAD,PAD
~~~

注意 `attention_mask` 的形状是 `[B,L]`，因为它服务于整段 `prompt + response` 前向；`response_mask` 是 `[B,T]`，因为 PPO 只在 response 区间计算训练目标。它们不能互相替代。

## 1. 前向：attention mask 与 causal mask 一起工作

~~~python
out = policy(
    input_ids=full_ids,              # [B, L]
    attention_mask=attention_mask,   # [B, L]
)
logits = out.logits                 # [B, L, V]
values = out.values                 # [B, L]，来自 value head
~~~

对位置 `i` 的 attention，真正允许看的位置是两层限制的交集：

```text
causal mask：只能看 j <= i，不能偷看未来 token
attention mask：j 必须不是 PAD
```

例如第 1 条在预测 `B2` 时可以看 `P1,P2,P3,B1`，不能看未来，更不能把两个 PAD 当作内容。

但这一步只保证模型的上下文处理正确；它**不决定**哪些位置应写入 PPO loss。即使 `attention_mask` 正确，若后面不使用 `response_mask`，PAD 仍可能进入 loss。

## 2. logits 如何对齐到 response token

decoder-only 模型在位置 `i` 的 logits 预测下一个 token `i+1`：

~~~python
shift_logits  = logits[:, :-1, :]       # [B, L-1, V]
shift_targets = full_ids[:, 1:]         # [B, L-1]

    dim=-1, index=shift_targets.unsqueeze(-1)
).squeeze(-1)                           # [B, L-1]

# prompt 长 Q=3：P3 的 logits 预测第一个 response token A1/B1
response_logp = all_logp[:, Q-1 : Q-1+T] # [B, T]
~~~

因此：

~~~text
response_logp[0] = [logp(A1), logp(A2), logp(A3), logp(A4)]
response_logp[1] = [logp(B1), logp(B2), logp(PAD), logp(PAD)]
~~~

最后两项虽然数值上可以算出来，但第 1 条的它们没有训练意义，必须被 `response_mask[1]=[1,1,0,0]` 排除。

## 3. rollout 时固定保存什么

用采样时的 old policy 得到：

~~~python
old_logp   # [B,T]，同样只把 response_mask=1 的位置视为有效
old_values # [B,T]，从 values 的 response 区间切出
rewards    # [B,T]，通常终止 response token 承载 RM/总 reward

advantages = compute_gae(rewards, old_values, response_mask)
returns = (old_values + advantages).detach()
~~~

以第 1 条为例，GAE 的循环只应处理 `B1,B2`；一旦走到 PAD，就要停止 bootstrap/累积，绝不能让 `B2` 的 advantage 从 PAD 位置继续传过来。概念伪代码如下（省略 batch 维）：

~~~python
last_gae = 0
for t in reversed(range(T)):
    if response_mask[t] == 0:      # PAD
        advantages[t] = 0          # 占位；之后不会用于 loss
        last_gae = 0               # 不让 PAD 跨位置传播
        continue

    next_is_valid = (t + 1 < T and response_mask[t + 1] == 1)
    next_v = old_values[t + 1] if next_is_valid else 0.0
    delta = rewards[t] + gamma * next_v - old_values[t]
    last_gae = delta + gamma * lam * (last_gae if next_is_valid else 0.0)
    advantages[t] = last_gae
~~~

真实实现会更仔细地区分“EOS 终止”“截断后仍可 bootstrap”等情形；这里你先抓住边界：**PAD 既不是环境状态，也不是动作，不能贡献 reward、value 或 TD residual。**

## 4. PPO 更新：同一张 response mask 同时保护两条 loss

每个 mini-batch 中，当前 policy 用同一个 `full_ids` 重新前向，得到 `new_logp/new_values`：

~~~python
ratio = exp(new_logp - old_logp)              # [B,T]

per_token_policy = -minimum(
    ratio * advantages,
    clamp(ratio, 1-eps, 1+eps) * advantages,
)
policy_loss = (per_token_policy * response_mask).sum() / response_mask.sum()

per_token_value = 0.5 * (new_values - returns).square()
value_loss = (per_token_value * response_mask).sum() / response_mask.sum()
~~~

在第 1 条样本上，`B1,B2` 参与两个 loss；两个 `PAD` 都不参与。这样 policy 学“哪些真实 token 概率该调”，value head 学“这些真实前缀之后的回报是多少”。

可以把本例浓缩成一句代码审查清单：

```text
full_ids/attention_mask → 只负责正确前向
response_mask           → logp、PPO clip loss、value loss、各项 mean 的有效位置
response_mask（或等价 valid mask）→ GAE/returns 不跨 PAD 传播
```

## 已掌握的内容

### 1. RLHF、DPO 与 PPO 的位置

- SFT：用标准答案做监督微调。
- 偏好学习：`chosen` 应比 `rejected` 得分更高；DPO 直接用偏好对训练 policy，reference model 的约束隐含在目标中。
- RLHF/PPO：通常先训练 RM（reward model），再让 policy 通过 RM reward 改善生成；policy（actor）负责生成 token，value head（critic）预测未来回报，RM 在 PPO 阶段冻结。
- PPO 要重点防 reward hacking，例如 RM 因长度或重复文本误判高分。

### 2. PPO 的核心数据流

```text
prompt
  → old policy 采样 response（rollout）
  → 保存 old_logp、old_values、reward
  → GAE 得到 advantages；returns = old_values + advantages（detach 固定）
  → current policy 在同一 full_ids 上反复前向
  → new_logp/new_values
  → policy loss + vf_coef × value loss
  → optimizer.step()
  → 用更新后的 policy 进行下一批 rollout
```

- `old` 是**当前 rollout 刚生成时**的快照，不一定是“上一轮 iteration”。
- `old_logp`、`old_values`、advantages、returns 在该 rollout 的多个 PPO epoch 中固定；每次 `optimizer.step()` 后 `new_logp/new_values` 会变化。
- PPO 是近似 on-policy：同一 rollout 只复用有限个 epoch，之后丢弃并重新采样。

### 3. PPO clip、GAE 与 detach

- `ratio = exp(new_logp - old_logp)`，不能把两个 logp 直接相除。
- `A > 0` 时希望 ratio 上升；超过 `1+ε` 后该 token 的 policy 梯度停止继续推高。
- `A < 0` 时希望 ratio 下降；低于 `1-ε` 后该 token 的 policy 梯度停止继续压低。
- GAE 的 `A_t` 表示“实际采样到的后续回报”相对该前缀的 value 预测的惊喜程度；早位置的 advantage 会含后续 TD residual 的折扣累积。
- `advantages/returns.detach()` 使 policy loss 只能通过改 token 概率降低，不能通过篡改 value 预测来伪造更有利的 advantage；value head 仅通过 value loss 拟合固定 returns。

### 4. 参数与梯度路径

```text
shared Transformer / Q,V LoRA
    ├─ LM head    → logits → new_logp   → policy loss
    └─ value head → values → new_values → value loss
```

- LM head 自身只受 policy 相关 loss 影响；value head 自身只受 `vf_coef × value_loss` 影响。
- shared Transformer/LoRA 同时收到两条路径的梯度：
  `grad_shared = grad_policy + vf_coef × grad_value`。
- 因此共享 LoRA 可能有 actor/critic 梯度冲突；`vf_coef` 从 0.5 降为 0.1 时，所有 value 路径梯度（包括 value head 与 shared LoRA 的 value 分量）都变为原来的 0.2 倍，policy 路径不变。

### 5. batch、epoch、mini-batch 与监控

以 `rollout batch=8`、`mini-batch=2`、`ppo_epochs=3` 为例：

```text
一个 rollout batch：8 条新采样 response
每个 epoch：4 个 mini-batch；每条样本使用一次
3 个 epoch：12 次 forward/backward/optimizer.step
```

- epoch 1 就出现高 KL / 高 clip fraction：优先降低 learning rate，也检查 advantage/reward 尺度与梯度裁剪。
- 仅后续 epoch 才恶化：优先降低 PPO epochs 或设 target-KL early stop。
- KL/clip 正常但 value loss 高、explained variance 差：优先排查 critic/value target，而非先怪 policy。
- RM/return 要看 min/max、分位数、阈值比例和 top-K 样本，不能只看均值和标准差；MSE 会被离群值平方放大。

### 6. token 对齐与 mask（今天最重点）

- `attention_mask [B,L]`：前向时让 PAD 不作为 attention 的 key/value。
- causal mask：位置 `i` 不能看未来 `j>i`；与 attention mask 共同限制可见位置。
- `response_mask [B,T]`：只选择真实 response token 参与 PPO logp、GAE/returns、policy loss、value loss 和相关均值统计。
- decoder-only 对齐：位置 `i` 的 logits 预测 `i+1`；`all_logp` 由 shifted logits/targets gather 得到，response 从 `Q-1` 处切出。
- PAD 是 batch 对齐用的人为占位，不是 policy 真实采取的 action，也没有真实 reward、advantage 或 return；即使它形式上有 logits/value 数值，也必须 `response_mask=0`。
- 正确 masked mean：

```python
masked_mean = (x * response_mask).sum() / response_mask.sum().clamp_min(1)
```

- PAD 被误纳入时有两类后果：
  1. PAD 误差非零：制造假 loss/假梯度，critic 被推去拟合 PAD；
  2. PAD 误差恰为零：分母仍被扩大，真实 token 的 loss/梯度被稀释，指标会虚假变好。

你已手算确认：若 `response_mask=[1,1,0,0]`，

```text
per_token_policy = [-0.4, 0.2, -10, 8]
正确 policy_loss = (-0.4 + 0.2) / 2 = -0.1

per_token_value = [0.5, 0.3, 100, 50]
正确 value_loss = (0.5 + 0.3) / 2 = 0.4
```

GRPO 到时会重点拆这几个问题：

```text
同一个 prompt 为什么要采样 G 条 response？
每条 response 的 reward 如何做组内相对化？
A_i = (r_i - group_mean) / (group_std + ε) 与 PPO 的 GAE advantage 有何不同？
没有 value head 后，省掉了什么计算与不稳定源，又失去了什么？
policy ratio、clip 和 reference KL 在 GRPO 中如何保留？
同组 response 的 padding / token mask / loss 平均怎样实现？
组内 reward 全相同、标准差接近 0、长度投机时如何诊断？
```

先给一个准确的预告：GRPO 不是“完全不用 reward”，而是对同一 prompt 生成一组候选，用可验证奖励或 RM 分数比较它们；再把组内的相对好坏作为 advantage。典型形式是：

```text
prompt x
  → 采样 G 个回答 y₁…y_G
  → 每个得到 reward r₁…r_G
  → 在该组内标准化得到 A₁…A_G
  → 用 A_i 加权的、带 clip/KL 的 policy objective 更新
```

与今天 PPO 的最显著差别：PPO 借助 value head/GAE 给每个 token 状态估计基线；GRPO 用“同一 prompt 的多条回答互相比较”形成基线，所以通常不训练 value model。这会减少 critic 的显存与训练不稳定，但需要一次采多条候选，组内奖励质量也变得更关键。
