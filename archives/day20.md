## 二、LLM 应用接口基础

### 2.1 推理请求与采样参数

学习了从 logits 到 temperature、softmax、top-k/top-p 和采样的基本链路，并讨论：

- `temperature` 调整概率分布的尖锐程度；
- `top-k` 和 `top-p` 限制采样候选；
- `max_output_tokens`、`stop`、`seed` 及 frequency/presence penalty 的作用；
- 结构化抽取、工具选择和 evaluator 通常使用较低随机性，创意生成可适当提高随机性；
- 不同 Agent 角色可以使用不同推理配置。

### 2.2 Structured Output 不等于语义正确

Schema 只能保证字段、类型和枚举等结构约束，不能保证业务语义正确。例如：

```json
{
  "category": "refund",
  "refund_amount": 500
}
```

即使完全符合 Schema，也可能存在：

- 用户实际意图是物流咨询，而不是退款；
- 当前最多可退款 200 元，模型却提出退款 500 元。

因此完整校验链为：

```text
Schema 校验
→ 语义/业务规则校验
→ 权限校验
→ 状态迁移校验
→ 执行保障
```

### 2.3 Function Calling 与多工具选择

模型返回的是“调用工具的候选意图”，不是工具已经执行。完整链路为：

```text
模型选择工具和参数
→ Runtime 校验
→ Executor 执行
→ 以结构化 Observation 返回结果
→ 模型继续决策或生成回答
```

工具数量较多时，先由 Runtime 按权限、任务阶段和领域过滤，再通过工具检索或路由得到少量候选，最后交给模型做语义选择。真正可互换的同类实现应隐藏在同一个抽象工具后，由 Runtime 根据成本、可用性和延迟选择 provider；语义不同的工具应保持独立。

## 三、Schema 设计方法

复杂任务不应直接要求模型一次生成超长 Schema，而应按以下过程协同设计：

```text
任务目标
→ 模型提出澄清问题和假设
→ 提供成功、失败和边界样例
→ 分别设计输入、模型决策、工具和 Observation Schema
→ 对抗性审查
→ 生成测试矩阵
→ 版本化为 v1
```

今天明确区分了四类字段来源：

- 模型决定；
- 用户提供；
- Runtime 注入；
- 程序计算。

用户 ID、权限、最大可退款金额等可信事实不应由模型生成。超长 Schema 应拆成按步骤或按工具的小 Schema，并先用字段表审查 `字段/类型/是否必填/生产者/消费者/存在理由`，再查看机器 JSON Schema。

建议使用复杂度预算：字段不超过约 8 个、嵌套深度尽量不超过 2、每个字段必须存在明确消费者。大量 nullable/optional 字段通常意味着把多个动作或状态错误地混在了同一 Schema 中。

## 四、Context、State、Memory 与 Codex

### 4.1 三层状态

今天区分了：

| 层次 | 职责 |
| --- | --- |
| Model Context | 本次模型调用看到的指令、历史、工具结果和证据 |
| Application State | Runtime 保存的任务阶段、已完成步骤、重试和待执行动作 |
| External State | 数据库、订单、库存、权限等当前权威业务事实 |

对于业务事实，应以最新外部权威数据为准；对于系统允许做什么，应以开发者规则和业务策略为准。历史摘要只能帮助理解，不能替代当前数据库事实。

### 4.2 短期记忆、长期记忆与状态机

- 短期记忆服务于当前任务；
- 长期记忆保存经确认、值得跨任务复用的信息；
- 状态机显式规定当前阶段允许哪些动作；
- 动态业务事实不应仅存入自然语言摘要。

Schema 校验参数形状，业务校验操作是否合法，状态机校验当前时机是否允许执行，三者不能互相替代。

### 4.3 结合 Codex 理解外部化状态

Codex 的 compaction 解决长对话的上下文容量、成本和连贯性问题，不是业务状态机。当前学习仓库已经形成轻量的外部化状态：

```text
AGENTS.md              → 稳定工作规则和模式切换
study_agent/STATE.md   → 当前学习进度
ROADMAP.md             → 长期路线
archives/ 和 qa/       → 历史证据
Git 工作区             → 文件真实状态
```

`AGENTS.md + STATE.md` 属于由模型遵循的软流程。高风险领域应使用代码状态机、受限工具和服务端校验形成硬边界。聊天被压缩后，应重新读取外部状态，而不是依赖模型保留全部历史细节。

## 五、Agent Loop、失败恢复与 Guardrail

### 5.1 Agent Loop 的核心对象

```text
TaskState
→ LLM 产生候选 Action
→ Runtime 校验并执行
→ 得到 Observation
→ 记录 Event
→ 更新 TaskState
```

LLM 负责概率性的语义决策，Runtime 负责确定性的控制与执行。工具输出也需要 Observation Schema、来源、时间和版本。

### 5.2 失败分类与幂等

今天区分了：

- 模型输出格式错误；
- 语义或业务规则错误；
- 临时基础设施错误；
- 执行结果未知；
- 上下文或状态不一致。

`refund_order` 超时不等于退款失败，可能是服务端已成功但响应丢失。此时进入 `RESULT_UNKNOWN`，使用原幂等键查询权威执行记录；只有确认未执行时，才考虑复用同一幂等键重试。不能直接再次退款，也不能为重试生成新幂等键。

Agent loop 还应设置最大步数、同动作重复次数、重试次数、总时长和成本等停止条件，并使用持久 State、Event Log 和外部事实进行恢复。

### 5.3 高风险操作与人工确认

确认必须绑定具体动作、参数、数据版本、有效期和确认 ID，不能只保存 `user_confirmed=true`。推荐将高风险工具拆为：

```text
prepare_refund
→ 生成不可执行的 Proposal
→ 用户确认具体 Proposal
→ commit_refund
```

若确认后的 `order_version` 或可退款金额发生变化，原 Proposal 和确认均失效。Runtime 不得继续执行，也不得擅自修改金额，而应生成新 Proposal 并重新确认。

### 5.4 Prompt Injection 与最小权限

用户输入、网页、邮件、文档、RAG 片段和普通工具文本默认是不可信数据，即使其中写着“管理员指令”，也不能升级为系统指令。Runtime 应按当前状态只暴露完成任务所需的少量工具，并限制文件、网络和敏感数据权限。

安全来自多层机制：

```text
标记内容来源与身份
→ 裁剪工具权限
→ 模型提出候选动作
→ Schema/业务/权限/状态校验
→ 高风险确认
→ 受限执行
→ 输出脱敏和审计
```

## 六、RAG 导入

今天只完成 RAG 的第一轮系统导入：

```text
离线：文档 → 解析 → Chunk → Embedding → Index

在线：Query → 召回 → 过滤/重排 → Context Builder
     → LLM 生成 → 引用与结果校验
```

结合推荐系统经验，将 Query/Chunk embedding、召回和 reranker 类比为推荐的召回与排序；区别是 RAG 的目标是找到足以支撑正确回答的证据，还必须关注来源、权限、版本和有效时间。

初步明确职责边界：

- 政策、手册、FAQ 等非结构化知识适合 RAG；
- 当前订单、余额、库存、权限和可退款金额等精确动态事实适合业务工具；
- 复杂问题通常使用 `RAG + Tool + Runtime`，关键金额与业务结论由确定性程序计算，LLM 负责理解和解释。
